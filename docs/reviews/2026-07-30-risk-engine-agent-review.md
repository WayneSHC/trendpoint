## 結論摘要

這支影片跟前一支（WMA）性質完全不同：**它談的是系統層，而系統層正是 TrendPoint
目前最薄的一環**。前一支影片的三個要素有兩個已經在系統裡；這一支反過來——
它的核心主張（風控引擎有最高決定權）在 TrendPoint 幾乎不存在。

| 影片主張 | TrendPoint 現況 | 判定 |
|---|---|---|
| A. 資金分配上限（Kelly） | **無風險預算**：現貨 sizing 全額投入、期貨實質槓桿 ~8.8x | **真缺口（最高優先）**，但**不要用 Kelly** |
| B. 最大回撤限制（Drawdown Limit） | MDD 只是報表指標；唯一守門是「權益 ≤ 0 爆倉」 | **真缺口**，且現成材料已備（monte_carlo 未接線） |
| C. 新聞防護（News Guard） | 完全沒有 | 真缺口，但需台股化（不是 FOMC 而是結算日） |

| F. Alpaca 模擬交易 / 自動下單 | **完全沒有下單層**（只有告警推播） | 不適用（Alpaca 不交易台股台指期） |

**一句話回答**：這支影片對 TrendPoint 的價值集中在 **A、B、C 三項風控缺口**，
而且它們是真缺口——不是「可以更好」，是**現在完全沒有**。至於它的技術架構部分
（MCP／Alpaca／反思迴圈），對這個專案不適用甚至有害。

**影片最有價值的其實是最後那段話**：不要指望 AI 生出通用賺錢策略，護城河來自
獨特的資料視角，系統的作用是確保不會因風險管理不當而爆倉。這句話與本 repo 的
憲章與 `run_ablation.py` 的判讀原則同向——值得直接引用，而非再論證。

## 一、真缺口 A：sizing 沒有風險預算（最高優先）

這是本次審查最重要的發現，而且與影片主張直接對應。

### 現貨：全額投入，單一部位曝險 100% 權益

`trading_costs.py:122-125`：

```python
def size(self, equity: float, price: float) -> float:
    max_affordable = equity / (price * (1.0 + self.commission_rate))
    return self._round_to_lot(max_affordable)
```

**「最大可負擔股數」＝ 把全部權益押進單一部位**。沒有每筆風險上限、
沒有部位上限、沒有依波動調整。這不是保守或積極的選擇問題——是這一層
**根本沒有風險概念**：它回答的是「我最多買得起幾張」，而不是「我應該買幾張」。

### 期貨：實質槓桿約 8.8 倍

`trading_costs.py:174-179` 的 `size()` 搭配 `config/config.yaml:99-100`
（`margin_rate: 0.055`、`margin_utilization: 0.5`）：

```text
權益 100 萬 → 可用保證金 50 萬
每口保證金（TX 22,000 點）= 22,000 × 200 × 5.5% = 242,000
口數 = floor(500,000 / 242,000) = 2
名目值 = 2 × 22,000 × 200 = 8,800,000 → 實質槓桿 8.8x
→ 名目 1% 逆向波動 = 權益 -8.8%
```

`margin_utilization: 0.5` 看起來像「只用一半資金、很保守」，但它管的是**保證金**，
不是曝險。在 5.5% 保證金率下，用一半資金＝約 9 倍名目槓桿。台指期日內
2% 的波動就是權益 -17.6%。

### 為什麼**不該**照影片用 Kelly

影片主張以凱利公式設資金分配上限。這在數學上正確、在本專案的實務上危險：

1. **Kelly 需要已知且穩定的勝率與賠率**，實務上只能用歷史估計。估計誤差
   `SE(p) = sqrt(p(1-p)/N)`，而本 repo 的交易樣本數很小——spec 011 記錄的
   TXF 全歷史回測基準只有 **2 筆進場**。用 2 筆估出來的 p 去算 Kelly，
   分母是雜訊，結果是災難性的過度下注。
2. **Kelly 最佳化的是長期幾何成長率，不是生存機率**。全 Kelly 的期望回撤極深
   （理論上有 1/2 機率經歷 50% 回撤），與影片自己 B 項的「回撤上限」互相打架。
3. **本 repo 已有更好的材料**：`monte_carlo.py` 的重抽分布，其 docstring 寫得
   比影片更到位——「95 百分位的回撤才是真正該準備承受的風險預算」。

**建議路徑**：不做 Kelly，改做**固定風險比例 + 波動率標準化**——
每筆風險 = 權益的固定百分比，部位大小由該百分比 ÷（ATR × 停損倍數）反推。
ATR 已經在系統裡（`ladder_system.calculate_atr`），吊燈停損距離也已知
（`chandelier_multiplier`），所以這條路**不需要任何新指標**，只需要改
`PositionSizer` 的一個實作，且 `for_asset_class` 工廠（`trading_costs.py:190`）
已經是可插拔設計——這是 spec 008b 留下的擴充點。

## 二、真缺口 B：回撤限制不存在（現成材料未接線）

`performance.py:39-64` 的 `max_drawdown_stats` 與 `monte_carlo.py` 的
95 百分位回撤，目前**都只是印出來給人看的數字**
（`run_backtest.py:53-54` 只 `print`，沒有任何約束消費它）。

唯一真正會動作的守門是 `backtester.py:538-576` 的爆倉防護：

```python
# spec 008b FR-011 爆倉防護：權益 ≤ 0 當根以當根收盤強制結清並終止
```

**權益 ≤ 0 才觸發——那是「已經死了才通知」，不是風控。** 在它與「正常交易」
之間沒有任何中間層：沒有「回撤達 X% 縮減部位」、沒有「回撤達 Y% 停止新進場」。

這是本次審查中**最容易實作、材料最齊備**的一項：

- 權益曲線在回測迴圈中已逐根維護（`backtester.py:529-531` 已算 unrealized）
- 峰值與回撤的計算已存在（`performance.py:44`）
- 風險預算的來源已存在（`monte_carlo.py` 的 p95 MDD）

缺的只是把它們接起來，並讓「回撤上限」成為 config 參數。順帶說明：
這一項對回測與實盤**都**有意義——回測裡它會改變績效（部位被縮減），
所以必須走「預設關閉 + 消融對照」的同一套紀律，理由與 spec 012 相同。

## 三、真缺口 C：事件封鎖（News Guard），但要台股化

影片的 News Guard 是「FOMC 前後自動停止下單」。概念可取，但**照搬美股行事曆
對台指期是錯的**。台股/台指期的等價事件依重要性排序：

1. **台指期結算日**（每月第三個週三）——結算前後的價格行為與平常不同，
   且近月合約在結算日換約（`data_sources/rollover.py` 已處理資料層的轉倉，
   但**交易層完全沒有結算日概念**）
2. **夜盤與日盤的跳空**——台指期夜盤（15:00–05:00）與日盤之間的跳空是
   系統性風險，現行回測是日線、看不到這一層
3. **除權息**（現貨標的，影響 0050/2330 等）
4. **美國 FOMC / CPI 公布**——影響台指期夜盤，屬影片原意，但優先序在後

**判定**：概念有價值，但需要一份台股事件行事曆作為新的資料來源，
成本明顯高於 A 與 B。建議**排在 A、B 之後**，且先只做第 1 項（結算日），
因為它的日期規則是確定的（第三個週三），不需要外部資料源即可實作。

## 五、不適用或應拒絕的部分

### E. MCP 讀 TradingView + Pine Script —— 不適用，且是降級

repo 的資料層（spec 008a/010）已接 **TAIFEX 官方源**（1998 起全歷史回填 + 每日增量）
並以 **FinMind 交叉驗證**（`verify_futures_data.py` 為哨兵）。TradingView 是二手
資料且授權條款不允許系統性抓取；Pine Script 對一個 Python 專案是負資產
（演算法要能被 pytest 斷言，寫進 TradingView 就驗不了）。

**唯一可取的一點**：MCP 讓 AI 直接讀資料而非截圖。這件事在本 repo 已經成立——
Claude Code 直接讀 SQLite 與原始碼。

### F. Alpaca 模擬交易 / 自動下單 —— 標的不符，且順序錯了

Alpaca 是美股/美期券商，**不交易台股與台指期**。台灣要走永豐 Shioaji、
群益 Capital 或元大的 API。更關鍵的是順序：repo 目前**完全沒有下單層**——
`monitor_signals.py` 只做訊號檢測與推播（LINE/Telegram，無憑證時走 Mock）。

**在 A、B、C 三個風控缺口補上之前接下單層，是把問題放大而不是解決。**
以現況的 sizing（現貨全額、期貨 8.8x）接自動下單，等於把「沒有風險預算」
從紙上搬到真錢上。這正是影片自己 #1 主張要防的事——它的架構順序（先自動化、
後風控）與它自己的核心理念矛盾。

### G. 反思迴圈（AI 每筆交易後評分自我修正）—— 應明確拒絕

這一項不只是「不適用」，是**與本專案的工程基礎直接衝突**：

1. **違反憲章原則 VI（可重現性）**：LLM 輸出非決定性。同一份歷史資料跑兩次
   可能產生不同的訊號序列，回測結果不可重現——回測就失去意義了。
2. **它就是一台過擬合機器**：每筆交易後用剛發生的結果修正規則，等於反覆用
   樣本內資訊調參。這與 `walk_forward.py` 的整個設計意圖（只信樣本外成績單）
   正面對撞。
3. **無法通過憲章原則 III**：每條驗收標準須對應至少一個 pytest 測試。
   你沒辦法對「LLM 給這筆交易打幾分」寫斷言。

若真想要「交易後分析」，正確做法是**離線的、決定性的**歸因分析：
把每筆交易的當時環境（ADX、ATR 分位、regime 狀態）記錄下來，
事後以統計方式分群檢視——這不需要 LLM，也不會污染訊號邏輯。

## 六、建議：一個「風險引擎」spec 的雛形範圍

若要採納，建議收斂為**單一 spec、三段交付**，優先序如下（與影片的排序不同，
理由是「材料齊備度」與「不需新資料源」）：

| 段 | 內容 | 為何這個順序 |
|---|---|---|
| **1. 回撤上限** | 權益回撤達門檻 → 停止新進場／縮減部位；門檻預設值由 `monte_carlo` p95 MDD 提供參考 | 材料全部現成（權益曲線、峰值計算、風險預算來源），零新資料源 |
| **2. 風險化 sizing** | 新增 `PositionSizer` 實作：每筆風險 = 權益固定比例，部位由 ATR × 停損倍數反推 | `for_asset_class` 工廠已是可插拔設計；ATR 與停損距離皆已存在 |
| **3. 結算日封鎖** | 台指期結算日（第三個週三）前後停止新進場 | 日期規則確定，不需外部行事曆；其餘事件（除權息／FOMC）另案 |

**共同紀律（與 spec 012 同）**：三項一律**預設關閉**、納入 `run_ablation.py`
消融清單、以扣成本後期望值/PF/MDD 裁決。理由很實在——回撤上限與風險化 sizing
都會**改變回測績效**（不像 spec 012 只是多一道濾網），所以「關閉時逐筆位元不變」
的回歸錨點更加不可或缺。

**特別提醒**：風險化 sizing 幾乎必然**降低**總報酬（曝險下降），
但應**提高**風險調整後指標（Calmar、MDD）。若用總報酬當裁決指標，
這個功能會被誤判為「有害」而砍掉。這是驗收指標必須事先講定的原因。

### 後續進度（2026-07-31 補記）

上表的**第 1 段（回撤上限）與第 3 段（結算日封鎖）**已合併為
[`specs/013-entry-gate-risk-limits/`](../../specs/013-entry-gate-risk-limits/)，
A 段（離線可驗收部分）已實作：`risk_gates.py` + `backtester.py` 接線，
兩道閘門**預設關閉**，關閉時逐筆逐根逐欄與實作前相同。

上面「特別提醒」那段在實作中兌現成了具體修正：`run_ablation.py:107-113` 原本的
判讀啟發式（「停用後報酬未惡化且交易數增加 → 該濾網只在扼殺樣本數」）**會把
一道正常運作的風控印成應該移除**——停用回撤閘門必然使總報酬上升、交易數增加。
spec 013 T029 已將風控列改以 MDD／Calmar 惡化為判讀依據，並在輸出表補上 Calmar
與期望值兩欄。

**第 2 段（風險化 sizing）尚未開案。** 另外，A 段實作中發現一個當時未預料到的
結構性性質：單標的路徑下，**空手且已封鎖的帳戶無法自行恢復**（沒有部位就沒有
權益變動，回撤永遠停在封鎖時的水位），故 `dd_resume_pct` 的解除路徑只在
「封鎖時仍持倉、其後未實現損益回升」才走得到。這不是 bug，但它使回撤閘門在
單標的回測中的實際語意接近「觸發後停止交易」而非「暫停後復原」——
B 段實測解讀時必須把這點算進去。
