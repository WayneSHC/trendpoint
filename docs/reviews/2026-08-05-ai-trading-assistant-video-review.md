## 結論摘要

**這是一支「工具教學」影片，不是策略影片。** 它教的是用 Claude Code
從零打造個人交易助理儀表板，四個步驟為：plan mode 規劃 → accept edits
建骨架 → 依個人流程加分頁 → 用 routines 排程每日互動。

TrendPoint 本身就是用這套方法做出來的，而且每一步都走得更遠：

| 影片步驟 | TrendPoint 現況 | 判定 |
|---|---|---|
| 1. plan mode 規劃功能 | Spec Kit 全流程（`/speckit-specify`→`plan`→`tasks`→`implement`），14 個 spec 目錄含 research/data-model/contracts | **已有且更嚴**，plan mode 是其子集 |
| 2. accept edits 建骨架 | 已建成：回測引擎、成本模型、walk-forward、消融、Streamlit 四分頁 | 不適用 |
| 3. 加分頁／自訂指標 | `app.py:621` 已有「價格與訊號／績效分析／風險分析／交易日誌」 | 已有 |
| 4. routines 每日排程互動 | `.github/workflows/alert_scheduler.yml:7` 交易時段每 30 分鐘自動推播 | 已有，且是無人值守而非問答式 |

**四個步驟沒有一個可以採納。**

但影片要打造的那個**東西**——「追蹤你的交易、標記重複犯的錯」——
指向一個 TrendPoint 真的沒有的東西，而且是我查證後確認的：

> **推播出去的訊號，系統從來不記得後來發生了什麼。**
> `sent_alerts` 表只有四欄 `(ticker, bar_time, alert_type, sent_time)`
> （`monitor_signals.py:44-51`），是純去重鍵——沒有價格、沒有方向、
> 沒有當時的指標狀態。因此「過去半年推播的 MSS 訊號，事後三天的報酬
> 分布長什麼樣」這個問題，**現在無法回答，且永遠無法回溯回答**。

**一句話回答**：影片的方法論對本專案是降級，不需要採納任何一步；
但它的目的（建立對自己實際輸出的回饋迴路）點出一個真缺口，
而這個缺口恰好可以解開 2026-07-30 審查留下的那個死結。

## 一、為什麼這個缺口值得補：它解開了 7/30 留下的死結

`2026-07-30-tradingview-mcp-workflow-review.md` 的結論是：

> 現貨盤中推播走 5 分線 + 硬編碼結構參數，**從未被任何回測驗證過**；
> 而且「對齊時框」在現行資料源下**不可行**——yfinance 的 5m 只給 5 天
> （約 270 根），`ma_period=200`、`chandelier_period=22` 跑不出統計意義。
> 要驗證得先換資料源，那是獨立且更大的案子。

該結論成立，我複查後沒有異議。但它只證明了「**回溯**驗證不可行」。
它沒有處理另一條路：

> **拿不到過去的 5 分線歷史，不代表拿不到未來的。**

排程每 30 分鐘就會下載一次最近 5 天的 5 分線
（`monitor_signals.py:167`），一天 9 次、一週 45 次。這些資料現在
用完即丟。若在推播當下把該訊號的價格與上下文寫下來，事後再回填
「N 根之後價格到哪」，那麼**每一次推播都在為自己累積樣本**——
不需要換資料源，不需要歷史 5m，只需要開始記。

一年約 240 個交易日 × 每日推播數，樣本會自己長出來。這不是回測的
替代品，但它是**目前唯一能對這個盤中面做出經驗判斷的路徑**。

需要說清楚的是：這**不會**讓盤中推播變成「回測驗證過的訊號」。
它產生的是前瞻性的觀察樣本，沒有成本模型、沒有出場規則、沒有
walk-forward，因此**不得**拿它的數字宣稱策略績效（憲章原則 II）。
它能回答的是更基本的問題：這些推播到底有沒有資訊量、哪一類
（MSS/BOS/關價）比較有、哪個時段特別差。

## 二、事實核對：現在到底記了什麼

| 項目 | 現況 | 依據 |
|---|---|---|
| 推播去重 | `sent_alerts` 四欄，主鍵 `(ticker, bar_time, alert_type)` | `monitor_signals.py:44-51` |
| 推播當下的價格 | **只進訊息字串，未落庫** | `monitor_signals.py:220,227,238,245` |
| 推播當下的階梯／關價／ATR | **只進訊息字串，未落庫** | 同上 |
| 事後結果 | **完全沒有** | 全 repo grep 無任何回填路徑 |
| 「交易日誌」分頁 | 是**回測**產生的 `df_trades`，非真實成交 | `app.py:953-969` |

所有數值在 f-string 裡組完就丟掉。`sent_alerts` 的語意被明確定義為
「已通知使用者」（`alerts.py:137`、`tests/test_monitor_signals.py:212`），
是通知層的狀態，不是研究資料。

## 三、若要做，這裡是必須先解決的問題（不是小事）

我原本想直接建議開 spec，查完之後認為**不能**——有一個先決條件沒解決，
現在開會做出一個不可信的資料集：

### 3.1 排程環境的 DB 是 actions/cache，不是持久儲存

```yaml
- name: 還原 SQLite 資料庫快取
  uses: actions/cache@v5
  with:
    path: trendpoint.db
    key: trendpoint-db-${{ github.run_id }}
    restore-keys: trendpoint-db-
```
（`.github/workflows/alert_scheduler.yml:35-41`）

GitHub Actions cache 有 7 天未使用逐出與倉庫總量上限，且 `restore-keys`
是前綴比對取最近一筆。這對「去重」是可接受的（最壞情況是重送一則通知，
這也是**現存**的既有行為，值得單獨記一筆），但對「研究資料集」是致命的：
**樣本會在你不知情的時候消失一段，而且缺漏不可見。**

一個有洞的樣本集比沒有樣本集更危險——它看起來可以算統計量。

**因此第一步不是寫記錄邏輯，是先決定資料放哪。** 三個候選：

| 方案 | 優點 | 代價 |
|---|---|---|
| 每輪 append 到 repo 內 JSONL 並 commit 回來 | 持久、可版控、可 diff、零外部相依 | 每日約 9 次 commit 汙染歷史；需處理併發與 write 權限 |
| 每輪上傳 artifact | 不動 repo | 有保留期限（預設 90 天）、要下載才能用，且不能累加 |
| 外部儲存（如 Gist／雲端 DB） | 持久且可累加 | 新增外部相依與憑證，違反目前「憑證只走 secrets、無外部狀態」的簡潔性 |

我傾向第一案的變體：**每個交易日收盤後彙整一次、單日一筆 commit**，
而非每輪都寫。但這需要使用者決定能否接受 repo 內多一份自動更新的資料檔。

### 3.2 「事後結果」的回填也要有地方跑

記下推播當下只是一半，還要在 N 根之後回頭看價格。5 分線在 yfinance
只留 5 天，所以回填視窗必須 ≤ 5 天，而且必須有一個排程去做——
不能等到人想看的時候才算（那時資料已經過期消失）。

這使本案的實際範圍比「多寫一張表」大：**它是一條新的資料管線**，
有自己的排程、保存策略與缺漏處理。

### 3.3 三條紅線的落點

| 紅線 | 本案落點 |
|---|---|
| 看前偏誤（原則 I） | **不適用但要防呆**：全部是事後記錄，不進訊號鏈。但必須確保這張表**永遠不被** `ladder_system` / `backtester` 讀取，否則就成了未來函數的入口 |
| 摩擦成本（原則 II） | 這批數字是**原始價格變化**，非策略績效。文件與 UI 都必須標明，不得與回測 KPI 並列比較 |
| 參數集中（原則 V） | 回填視窗長度、記錄開關一律進 `config/config.yaml` + Pydantic |

另外照既有慣例：**總開關預設關閉**（同 spec 012/013/014），
關閉時逐筆行為與實作前相同。

## 四、影片中不建議採納的部分

**情緒筆記與人為紀律標記。** 影片（依摘要）強調把交易依「setup／
時段／部位大小／情緒註記」分群，找出「70% 的虧損來自開盤前十分鐘」
或「贏了之後加碼」這類模式。這是**主觀交易者的日誌方法論**，
前提是「你在手動下單、而且會犯紀律錯誤」。

TrendPoint 沒有下單層，推播的定位是盤中提示（CLAUDE.md 監控段）。
把情緒欄位搬進來，記錄的是使用者的手動行為，那是另一種產品，
不是這個 repo 的職責範圍。**建議只記系統自己的輸出，不記人的行為。**

**AI 自動下單／agentic 帳戶。** 搜尋過程中週邊資料大量出現「讓 Claude
連接券商帳戶自動下單」的做法。這與本專案的既有立場直接衝突——
7/30 審查已定調：「凡是會影響訊號或資金的判定，必須是確定性的程式碼，
並有測試守門」。不採納，也不建議討論。

## 五、建議行動

**本次不開 spec，不改任何程式碼。** 理由是第三節：資料落點未定之前
動手，會做出一個有洞且不可信的資料集。

留給使用者的決定，只有一個問題：

> **要不要開始累積「推播訊號的事後表現」這份資料？**
> 若要，前置決定是資料放哪（3.1 三個方案），我建議
> 「每日一筆 commit 進 repo」。決定之後才值得走 Spec Kit。

若答案是「要」，spec 的合理範圍是：

1. 推播當下落庫：訊號類型、方向、價格、階梯／關價、bar_time、時框
2. 排程回填：N 根之後的價格（N 進 config，視窗 ≤ 5 天受資料源限制）
3. 儀表板新增唯讀分頁：依 `alert_type` 分群的前瞻報酬分布
4. 防呆測試：確保該表不被任何訊號／回測路徑讀取
5. 總開關預設關閉

若答案是「不要」，那本次審查的產出就只有這份文件，這也是合理結果——
影片本身確實沒有可採納的內容。

**順帶記一筆（與本案獨立）**：`sent_alerts` 存活於 actions/cache，
快取逐出時去重會失效並重送通知。這是既有行為、影響輕微（重複一則通知），
但先前沒有文件記錄過，列此備查。
