## 結論摘要

> **`data_sources/yfinance_source.py:17` 原註解稱「5 天是 yfinance 對 5m 的上限」——不正確。**
> Yahoo 對 `5m` 的回溯上限是 **60 天**；7 天是 `1m` 的限制。
>
> 這個前提外溢成了結論：2026-07-30 review 第五節據「5m 只有約 270 根、
> `ma_period=200` 連 1.35 個週期都跑不完」判定盤中系統跑不出統計意義，
> 並把「真正的盤中系統」封存於「前置是換 5m 資料源」。
>
> **實測：單檔 3,132 根（59 交易日），是原估的 11.6 倍。**

實測 8 檔台股後：**46 個來回交易，跨過推論門檻 30**。盤中系統**現在就可評估**，
免費、零安裝、可進 CI——**不需要 TradingView，也不需要贊助 FinMind**。

## 一、原問題的答案：TradingView MCP 不必採用

`github.com/coocolab/Coocolab-Tradingview-MCP`（`tradesdontlie/tradingview-mcp`
的繁中改編版，31 stars，MIT）。詳細比較見本節末的判定表。

**三條硬性阻擋**：

1. **執行環境不相容**——需 GUI + 登入的 TradingView Desktop + CDP 埠 9222。
   TrendPoint 的自動化全是 headless（`alert_scheduler.yml` cron、
   `research_b_segment.yml`、Streamlit server）。
2. **授權紅線**——README 明文禁止「以擷取資料做自動化交易決策」與資料再散布，
   直接命中 `monitor_signals.py` 與 `data_ingestion.py`。
3. **資料完整性**——其連續合約 back-adjust 規則不透明，給不出 spec 011 要求的
   `unadj_*`（`backtester.py` 對缺欄硬失敗，這是對的）。

**安裝前應知的風險**（非道德批評，是工程判斷）：

- repo 根目錄有 `scalper-run.js`——BitGet **XRP/USDT 實盤自動下單機器人**，
  無人工確認，另含繞過交易所反洗盤鎖定的重試迴圈。**與其 README 自陳的
  「不適用於生產自動交易」直接矛盾。**
- `safety-check-log.json` 是**真實成交紀錄**（含真實 BitGet 訂單 ID）。
  作者把自己的實盤日誌 commit 進了公開 repo。
- `SECURITY.md` 承認除「只綁 localhost」外**無任何存取控制或身分驗證**。
  任何能在該機器執行程式碼的東西（含 npm postinstall）都能接管該 Electron
  實例、讀取已登入的 TradingView session。

**唯一與交易無關但有價值的收穫**：其 `RESEARCH.md` 的實測結論是
「**工具數量不是制約，輸出大小才是**」（緊湊輸出把工作流從 80KB+ 降到 5–10KB），
並在自己的 `CLAUDE.md` 裡把它制度化成**輸出規模預期表**與硬上限。
TrendPoint 的鐵律 2 有行為規則（「大檔先 Grep」）但**沒有量化預期**
（哪些算大檔、讀一次多少）。補一張檔案規模表是低成本改進，見第五節。

| 該工具的能力 | 對 TrendPoint 的判定 |
|---|---|
| `rules.json` 晨間掃描 | **不用**——自然語言規則交 LLM 判讀，不可重現、無法回測 |
| `alert_create` | **不用**——比現行 `alerts.py` + Actions 排程更脆弱（需桌面常開） |
| 讀圖分析 | **不用**——LLM 標記 swing point 不可重現（2026-07-30 review 第三節結論不變） |
| AI 自動調參 | **不用**——繞過 `optimizer.py` + walk-forward 的參數高原檢查 |
| `data_get_study_values` | **不用**——外部指標值引入不可控的計算定義差異 |
| `replay_trade` 當回測 | **不用**——無成本模型、無 walk-forward、無消融 |
| `data_get_ohlcv` 取 5m 歷史 | **原本是唯一候選，現已被 yfinance 取代**（見第二節） |

## 二、錯誤前提與更正

### 事實

```python
# 原（yfinance_source.py:17-19）
# 5 分線固定 5 天——那是 yfinance 對 5m 的上限，不是可調策略參數
_FIVE_MIN_PERIOD = "5d"
```

Yahoo 的實際限制：`1m` → 7 天；**`5m`（及其他 <1d 間隔）→ 60 天**。

### 影響鏈

| 環節 | 內容 |
|---|---|
| 錯誤前提 | 「5m 上限 5 天」 |
| → 推導 | 「5m 只有約 270 根」 |
| → 結論 | 「`ma_period=200` 連 1.35 個週期都跑不完，跑不出統計意義」 |
| → 決策 | 2026-07-30 review 第五節**封存**「真正的盤中系統」，並宣告前置是**換資料源** |

**實測後**：單檔 3,132 根 / 59 交易日 / `ma_period` 可跑 15.7 個循環。
封存決定所依據的算術是錯的。

### 已改

- `_FIVE_MIN_PERIOD` `"5d"` → `"60d"`，註解記錄更正與影響範圍
- **現行行為零改變**：`equity_instrument` 的 timeframes 僅 `["daily"]`
  （`instruments.py:90`），`run_ingestion.py:143` 只迴圈宣告的時框，
  故 adapter 的 5m 分支目前無呼叫端
- **`monitor_signals.py:167` 刻意不動**——它繞過 adapter 直接呼叫
  `fetch_stock_data(period="5d")`。盤中提示只需最近數日，拉長只增加每 30 分鐘
  一次輪詢的傳輸量而無收益
- `test_five_minute_period_is_not_config_driven` 的斷言改對齊模組常數。
  該測試守的不變式（5m period 不得跟隨 `equity_history_period`）**仍成立**；
  錯的是字面值與 docstring 裡重複的同一個錯誤說法

## 四、四個保留（此結論**不足以**支撐什麼）

1. **不能做 walk-forward**。期間只有 2026-05-14 → 08-06 **一個市況窗口**，
   切不出多組訓練/測試。
2. **Pooling 有方法論問題**。46 筆是 8 檔加總，但合取率從 2308 的 2.1% 到
   1301 的 15.8%（7 倍差）。混算隱含「參數對所有標的同樣適用」，
   而 config 本身有 `ticker_overrides` 即表示不成立。
3. **三檔掛蛋**（2330 / 2454 / 2308），46 筆中 31 筆來自 1301 與 2882 兩檔。
   正確表述是「盤中系統**在某些標的上**可評估」，非「盤中系統可行」。
4. **yfinance 資料飄動**。0050 在相隔 56 分鐘的兩次執行給出不同交易數
   （7 → 5 個來回），根數同為 3,132。此現象 `research_b_segment.yml` 已記錄；
   `probe_yfinance_5m.yml` 因此保留 CSV 快照與 sha256 指紋。

**在 walk-forward 與消融之前，本節任何數字都不構成對策略有效性的宣稱**
（憲章原則 III）。

## 五、本次調查中修正的自身錯誤（誠實聲明）

工具本身出過兩個回報層的錯，都會誤導判讀，已修正並記錄於此以免重蹈：

1. **交易數虛報一倍**。`res["trades"]` 是逐筆買賣明細（BUY / SELL_ALL 各一列），
   不是來回數。原本直接 `len()` 等於把腿數當交易數。
   **曾據此向使用者回報「0050.TW 14 筆」，實為 7 個來回。**
2. **結構訊號未分方向**。`bos_signal` 是三值（+1/-1/0），原以 `astype(bool)`
   計非零，等於多空合計，使【三】的 BOS 數與【三之二】的基數對不起來。

以合成資料逐根重放引擎迴圈驗證後鏈條自洽：
2,246 個多方 BOS → 15 根候選 → 12 筆進場（3 根因持倉中跳過）→ 24 列明細。
