| 影片工作流程 | TrendPoint 現況 | 判定 |

## 一、真問題：現貨監控與回測跑在不同時框

### 事實核對

| 路徑 | 時框 | 資料來源 | 依據 |
|---|---|---|---|
| 現貨**即時監控** | **5 分線** | yfinance 現抓（`period="5d", interval="5m"`） | `monitor_signals.py:164-168` |
| 期貨即時監控 | 日線 | DB 連續表 + 當日端點 | `monitor_signals.py:123-161` |
| 現貨/期貨**回測** | **日線** | DB `*_daily` 表 | `run_backtest.py:72,78` |
| 消融測試 | 日線 | 同上 | `run_ablation.py:128` |
| 儀表板 | 日線 | 同上 | `app.py:404,642` |

監控端呼叫指標組裝時，參數是**硬編碼常數**（`monitor_signals.py:179-181`）：

```python
df = ladder_system.build_indicator_frame(
    df, structure_period=10, include_regime=False,
    use_fvg=True, fvg_lookback=3)
```

### 三個後果

**(1) 結構窗的實際長度差 78 倍。** `structure_period=10` 在日線是 10 個交易日
（約兩週），在 5 分線是 50 分鐘。`detect_market_structure` 的
`rolling(window=period).max()` 因此在兩端偵測的是完全不同尺度的結構——
一個是波段高低點，一個是盤中噪音。

**(2) 現貨推播的訊號沒有回測基礎。** 回測驗證的是「日線 + 全套濾網 + config
參數」的系統；現貨推播的是「5 分線 + 僅結構訊號 + 硬編碼參數 + 無市況濾網
（`include_regime=False`）」。這兩者不是同一個系統的兩種呈現，**是兩個不同的系統**。
績效報表對前者成立，與後者無關。

**(3) 這比 spec 012 記錄的落差更嚴重。** spec 012 的 Assumptions 記錄了
「監控端未套用動能/趨勢/波動/全域四道確認」，當時我把它定性為「少幾道濾網」。
實際上時框也不同——**少幾道濾網是量的差異，換時框是質的差異**。
spec 012 的該段記錄需要更正。

### 這不是「缺多時間週期」，也不是失誤

> **【2026-07-30 複核更正】** 本節初稿寫「不是刻意的多時框協同，而是兩條路徑
> 各自選了時框、沒人對齊過」——**該推論錯誤**，複核後撤回。事實是：
>
> 1. **5 分線是刻意設計**。`monitor_signals.py:165` 註解明寫「下載最新 5 天的
>    5 分鐘線，以獲取最新即時資料」；且 `alert_scheduler.yml:7` 的 cron 為交易
>    時段每 30 分鐘一次——**這個節奏只有配盤中資料才說得通**。若改用日線，
>    每天僅一根新 bar，去重機制（鍵為 `ticker/bar_time/alert_type`）會使 9 次
>    輪詢中 8 次為 no-op。
> 2. **「對齊時框」在現行資料源下不可行**。`data_sources/yfinance_source.py:17`
>    的 5m 設定為 `("5d", "5m")`（約 270 根），且 yfinance 對 5m 本身有約 60 天
>    的 API 上限。`chandelier_period=22`、`ma_period=200` 在 270 根上跑不出統計
>    意義——要讓 5m 可被回測驗證得先換資料源，那是獨立且更大的案子。
>
> > **【2026-08-06 更正】本點的算術基礎錯誤，結論撤回。**
> > 本點自己寫出了「yfinance 對 5m 有約 60 天的 API 上限」，卻改以 repo
> > **當時硬編碼**的 `period="5d"`（約 270 根）作為推論基數——把「repo 目前抓多少」
> > 誤當成「資料源給得起多少」。兩者差 11.6 倍。
> >
> > 實測（run `31084877137`）：`period="60d"` 單檔得 **3,132 根 / 59 交易日**，
> > `ma_period=200` 可跑 15.7 個循環。`yfinance_source.py` 的常數已於 2026-08-06
> > 更正為 `"60d"`（PR #53）。
> >
> > 詳見 `docs/reviews/2026-08-06-intraday-timeframe-feasibility.md`。
>
> 因此**正確定性不是「該對齊的落差」，而是「一個刻意做出來、但從未被驗證過的
> 產品面」**。第一節開頭的事實陳述（現貨推播無回測基礎、參數硬編碼、時框差
> 78 倍）全部成立；錯的是把它讀成失誤。

影片的 MTF 是指「日線定方向、小時線找結構、5 分線抓進場」的刻意協同設計。
TrendPoint 沒有這種協同，但它也沒有「該協同而未協同」的問題——它有的是
一個定位清楚（盤中提示）但未經驗證的通知面。要不要處理，取決於使用者
如何看待這些推播，而非工程正確性。

## 二、順帶查到：`stock_*_5m` 表是死資料

`run_ingestion.py:114` 對每個 instrument 迴圈其 `timeframes`，而現貨
instrument 的預設 timeframes 是 `["daily", "5m"]`（`instruments.py:76-78`，
註解說明是為維持 008a 前的行為）。`app.py:331` 在新增標的時也會寫入 5m 表。

**但沒有任何分析路徑讀取這些表**：回測、消融、walk-forward、UI 圖表一律走
`table_name_for(inst, "daily")`；監控端的現貨路徑是**現抓** yfinance
（`monitor_signals.py:167`），不讀 DB 的 5m 表。

也就是說：每次 `run_ingestion.py` 都為每檔現貨多打一次 yfinance 的 5 分線 API、
多寫一張表，而這張表**只寫不讀**。

**建議**：二擇一，不要維持現狀——

- 若確認不需要 5m：把現貨 instrument 的預設 timeframes 改為 `["daily"]`，
  移除 5m 入庫路徑（減少 API 呼叫與 DB 體積）
- 若要保留 5m：讓監控端改讀 DB 的 5m 表而非現抓（減少對 yfinance 的即時依賴，
  並使監控與入庫用同一份資料）

這是小改動，但屬於「資料衛生」（憲章原則 VI），且與第一節的時框問題是同一個
根源：**5m 這條路徑當初留下來了，但沒人決定它到底要不要用**。

## 三、影片五點的逐條判定

### 1. 市場結構分析 —— 已有且更強

repo 的實作是確定性的程式：`detect_swing_points`（fractal，
`ladder_system.py:143`）、`classify_structure`（HH/HL/LH/LL → trend_bias，`:189`）、
`detect_market_structure`（BOS/MSS 分離，`:217`），且看前偏誤由
`shift(swing_n)` 防禦、有 `tests/test_lookahead_bias.py` 守門。

LLM 讀圖標記 swing point 的問題不是「不準」，是**不可重現**：同一張圖跑兩次
可能標出不同的點，於是無法回測、無法寫斷言（違反憲章原則 VI 與 III）。

### 2. 支撐壓力繪製 —— 已有等價物

三關價（`ladder_system.py:556-559`，以昨日高低 × 1.382 導出上下關價）、
ATR 階梯（`calculate_ladder_levels`）、吊燈線（`calculate_chandelier_exit`）
都是確定性的價位。影片的「AI 找出顯著關鍵價位」是主觀判斷的自動化，
不是新方法。

*（若真想擴充 S/R，值得考慮的是**成交量分布**或**swing 群聚**——但影片沒給方法，
這屬於另一個議題。）*

### 3. 指標與參數設定 —— 唯一可能有價值的小點

影片示範用 AI 搜尋並套用特定交易者的參數（如 Linda Raschke 的 MACD 3-10-16）。
這在 TrendPoint 的意義只有一個：**參數先驗的候選來源**。

但不能直接採用——repo 的整套方法論（`optimizer.py` + `run_walk_forward.py` 的
參數高原檢查）存在的理由，就是「別人的最佳參數在你的資料上未必成立」。
借來的參數與網格搜出來的參數一樣，都必須通過樣本外驗證。

**判定**：可作為縮小搜尋範圍的起點，價值有限，不需要為它做任何事。

### 4. 多時間週期分析 —— 見第一節

### 5. 策略回測與風控 —— 已有且更嚴

在 TradingView 裡用 AI 建立均線交叉策略並回測，相對 repo 現有能力是全面降級：
無成本模型（憲章原則 II 要求含手續費/稅/滑價）、無 walk-forward、
無看前偏誤防禦、無消融。

「精算每筆倉位大小」的方向是對的——但這正是同日第二份審查已指出的缺口
（`EquitySizer` 全額投入、期貨實質槓桿 8.8x），已由 spec 013（進場閘門）
與規劃中的 spec 014（風險化 sizing）處理。影片對此沒有提供方法。

## 四、關於「AI 作為交易助理」的定位

影片的核心定位——**AI 負責繪圖、計算與分析，最終決策與風險把關由人類負責**
——是對的，且與本專案現狀一致：`monitor_signals.py` 只推播告警、
不下單（repo 沒有任何下單層）；`app.py` 只呈現、不內嵌演算法邏輯
（CLAUDE.md 的 UI 規則）。

這一點不需要改變任何東西，但值得記下來：**它與影片自己示範的
「AI 自動控制圖表、自動套指標、自動回測」之間有張力**。定位講得對，
示範的工作流程卻在往「AI 做分析決策」走。真正該守的線是：
**凡是會影響訊號或資金的判定，必須是確定性的程式碼，並有測試守門**；
LLM 可以幫你探索想法、讀 code、寫 spec，但不能成為訊號鏈的一環。

> 提高樣本量的有效槓桿是**加標的**（46 筆中 31 筆來自 1301 與 2882 兩檔）。
