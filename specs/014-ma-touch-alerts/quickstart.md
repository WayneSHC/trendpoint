## A 段：離線驗收

```bash
pytest -q                              # 全綠為硬性關卡
pytest -q tests/test_ma_lines.py -v    # 純函式：均線計算 + 穿越判定
pytest -q tests/test_ma_alerts.py -v   # monitor 整合 + 既有告警回歸
pytest -rs                             # 逐條檢查 skip 理由
```

**`pytest -rs` 的意義**：本 repo 的踩坑教訓是「該跑卻跳過等於沒驗到」。
本案所有 A 段測試一律以合成資料執行，**不得**因缺 `trendpoint.db` 而 skip。

### 合成資料在本案比真實資料更好

核心測試都需要**精確控制**價格與均線的相對位置：

| 測試 | 需要的序列 | 合成方式 |
|---|---|---|
| SC-002 四條線各發一次 | 自各條均線上方跌破 | 構造遞減段，令價格依序穿過四條線 |
| SC-003 持續低於不重發 | 穿越後連續多根皆低於 | 跌破後維持低檔 |
| SC-004 同日反覆穿越至多一則 | 同一交易日內上下震盪 | 5 分線序列在均線附近來回 |
| SC-005 資料不足 | 僅 100 根日線 | 直接截斷日線 fixture |
| SC-006 均線值正確 | 已知收盤價序列 | 手算對照 |

真實資料無法保證這些邊界情境一定出現在測試窗內。

### SC-001 的驗收法（既有告警不變）

這是本案的最高風險項（FR-008），須以**三層**確認：

```bash
# 1. 總開關關閉（預設）時，對同一份固定 5 分線 fixture 執行 check_new_signals，
#    比對六種告警的產出集合與實作前完全相同
# 2. 確認關閉時**未讀取**日線表（以 mock 或計數器驗證 DB 讀取次數為 0）
# 3. 總開關開啟時，六種告警的產出集合仍與關閉時相同（只多出均線通知）
```

第 2 層特別重要——它證明關閉時是真正的短路，而非「讀了但沒用」。

## B 段：需真實資料（`[MANUAL]`）

### 前置

```bash
python run_ingestion.py            # 確保 stock_*_daily 有足夠歷史（年線需 240 根）
```

### SC-013：實跑觀察

```bash
# 於 config/config.yaml 開啟 alerts.ma_alerts_enabled: true 後
python monitor_signals.py --once   # 無憑證時走 Mock 分支，訊息印在畫面上
```

**觀察項**：

1. 均線值是否合理（可與看盤軟體的月／季／年線目視對照）
2. 訊息是否含 FR-009 的全部欄位（標的、線別、均線值、現價、乖離、時間）
3. **既有六種告警是否照常運作、內容未變**
4. 資料不足的標的是否被正確跳過（而非發出假均線）

### 儀表板現況表

```bash
streamlit run app.py
```

選一個現貨標的，確認均線現況表顯示四條線的位置與乖離，
且資料不足的線顯示「資料不足」而非空白或 0。
