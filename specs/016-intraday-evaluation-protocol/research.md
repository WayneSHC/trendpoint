# Phase 0 Research: 盤中時框評估協定

**Feature**: `016-intraday-evaluation-protocol` | **Date**: 2026-08-07

spec.md 進入本階段時無 `[NEEDS CLARIFICATION]` 殘留（唯一的 Q1 已由 D1 裁決）。
本檔處理的是**設計層的未定項**：Assumptions 給了預設值，但預設值的理由、
以及若干技術可行性問題，須在動工前釘死。

---

## R1：累積歷史的落地格式

**Decision**：**canonical CSV**——價格欄正規化至小數 4 位、量欄為整數、
索引為 UTC-naive 台北時間、欄序固定為 `datetime,open,high,low,close,volume`。

**Rationale**：

1. **不新增相依**。Parquet 需 pyarrow，是本案唯一會新增的第三方套件；
   憲章治理段要求「若新增依賴，須回答為何更簡單的做法不可行」——
   而 CSV 在此夠用。
2. **正規化同時解掉三個問題**：CSV 浮點往返的確定性（FR-003）、
   指紋穩定性（FR-004）、以及資料源微幅飄動被誤判為衝突（FR-014）。
   yfinance 對台股回傳的價格本質是 2 位小數，float64 的 1e-13 級雜訊
   若不截斷，會讓每週合併都報出數百筆假衝突，真正的資料修正就被淹沒。
3. **與既有契約相容**。`csv_source.py:30-38` 的解析契約與
   `run_5m_evaluation.py::load_csv` 皆吃這個格式，累積歷史可直接餵給
   既有工具，無需轉檔。
4. artifact 內容可被人直接開啟檢視——出問題時不必先裝套件才能看資料。

**Alternatives considered**：

- **Parquet**：浮點精確往返、檔案小。否決於新增相依，且正規化後 CSV
  的精確性已足（4 位小數對 2 位小數的原始資料是無損的）。
- **SQLite（`trendpoint.db`）**：否決。該庫本身 gitignored 且由 ingestion
  重建，把不可再生成的累積塞進可重建的庫是錯誤的耐久性假設；
  且 spec 015 已立下「不為觀察層新增表」的先例。
- **JSONL**（沿用 spec 015 的 `alert_log/`）：否決。那是**事件**流（逐筆告警），
  本案是**時間序列**，欄式表格是自然形狀；JSONL 會讓每根 K 線重複欄名。

## R2：跨執行取回前次 artifact 的機制

**Decision**：在 workflow 內以 `gh run list` 找出同一 workflow 最近一次
**成功**的 run，再以 `gh run download <run-id> -n <artifact-name>` 取回；
取不到時**不失敗**，而是標記為鏈結起點並將該事實寫入報告。

**Rationale**：

- `gh` CLI 在 GitHub-hosted runner 上預裝，以 `GH_TOKEN: ${{ github.token }}`
  即可運作，權限只需 `actions: read`。不引入第三方 action。
- 「取不到」有三種成因——首次執行、逾 90 天保留期、上次 run 失敗——
  三者對**資料**的後果相同（鏈斷了），對**判讀**的後果也相同（累積歸零），
  故不需區分處理，但**必須顯式回報**（FR-023）。
- 刻意鎖定「最近一次成功的 run」而非「最近一次 run」：失敗的 run 可能只上傳了
  半份資料，拿它續接會把破損資料寫進鏈裡。

**Alternatives considered**：

- `actions/download-artifact@v4` 搭 `run-id` 參數：可行，但仍需先用 API 查出
  run-id，等於多一個步驟卻沒少一次 API 呼叫。
- 第三方 `dawidd6/action-download-artifact`：功能更順手，但為了一個
  `gh` 兩行就能做的事引入外部 action，不符複雜度證成的要求。
- **GitHub Releases 或 Gist 作為儲存**：可繞開 90 天限制，但兩者都等同於
  「公開發布資料」，D1 接受的是 artifact 的曝光面，擴大到 Releases 是
  超出裁決範圍的決定。

## R3：資料源飄動時的合併取捨規則

**Decision**：**先到者為準**（already-accumulated wins）。既有累積值不被
後續取數覆寫；衝突次數與衝突時間戳的極值一併記錄於報告。

**Rationale**：

- **可重現性優先於新鮮度**。若採後到者覆寫，同一份累積歷史在不同週次會
  給出不同的歷史段，先前發出的結論就無法被重跑驗證——那正是本規格
  要修的缺陷 4。
- **它同時是一道看前偏誤防線**。Yahoo 對已收盤資料的事後修正，本質是
  「日後才知道的資訊」；讓它覆寫早先的評估窗，等於把未來資訊回填進
  過去的判定（憲章原則 I 的精神）。
- 衝突計數保留下來，是為了讓「資料源異常」不被這條規則掩蓋——
  若某週衝突數暴增，那是訊號，不該靜默吞掉。

**Alternatives considered**：

- **後到者為準**：資料品質上通常較優（修正過的值更正確），但代價是
  歷史會漂移。本案的核心訴求是可重現，故否決。
- **保留兩版並標記**：資訊最完整，但讓下游每個消費者都得處理「同一根 K 線
  有兩個值」，複雜度外溢到整條鏈。否決。

## R4：樣本外切分的實作 —— 是否重用 `walk_forward.py`

**Decision**：**不重用**，於 `intraday_snapshot.py` 自行實作 gap-aware 的
純切分函式（只回傳窗口邊界，不執行任何回測或尋優）。

**Rationale**：

1. `WalkForwardAnalyzer.run()`（`walk_forward.py:95`）把切分與**網格尋優**
   綁在一起（`_grid_search` 掃 `atr_periods` × `ladder_ks`，以 Calmar 選優）。
   **策略調參明列於本規格 Out of Scope**——在樣本外機制成立前調參即是過擬合。
   重用它會把明文排除的東西帶進來。
2. 它的切分假設**資料連續**（全樣本均分為 n_folds）。本案的累積歷史必然
   帶斷裂（排程中斷、假日、鏈結重起），FR-016 要求測試窗不得跨越斷裂——
   這是既有切分器沒有、也不該為它加上的語意。
3. 純函式切分（輸入索引與斷裂位置 → 輸出窗口邊界）可被單元測試逐窗比對，
   而 `WalkForwardAnalyzer.run` 要跑完整回測才看得到切分結果。

**Alternatives considered**：

- 改造 `WalkForwardAnalyzer` 使尋優可關閉：會動到日線生產路徑的既有行為，
  與 FR-019 的零改動保證衝突。否決。
- 直接呼叫 `WalkForwardAnalyzer` 但忽略尋優結果：仍會付出完整網格的計算成本，
  且報告中會出現「最佳參數」欄位——那正是不該出現的東西。否決。

## R5：納入準則的時序位置與維度

**Decision**：準則由**評估窗開始之前**的一段 lookback（預設 20 個交易日）計算；
lookback 與評估窗**不重疊**。維度四項：

| 維度 | 判定方式 | 為何客觀且事前可得 |
|---|---|---|
| 日內成交量水準 | lookback 期間日均量 ≥ 門檻 | 純市場屬性，與策略無關 |
| 資料完整度 | lookback 期間盤中缺口根數比率 ≤ 門檻 | 資料體質，與策略無關 |
| 每日根數穩定度 | 每日根數的變異係數 ≤ 門檻 | 資料體質 |
| 價格檔位粒度 | 相鄰價格最小非零差距 / 價格 ≤ 門檻 | 交易所規則的函數 |

**Rationale**：

- FR-010 只要求「不引用回測產出」，但**光是這樣不夠**。若準則用評估窗自身的
  資料計算（例如「評估期間日均量夠大」），納入決定仍受評估期間的市況影響——
  那是選擇偏誤的時序版本，形式上不算回測產出，實質上一樣污染結論。
  把 lookback 推到評估窗之前，才讓 FR-009 的「開始前即可得知」在字面與實質上都成立。
- 四個維度全是**資料體質與市場結構**，沒有一個牽涉報酬、勝率或訊號數——
  這是可被檢驗的分界線，也是 SC-005（擾動不敏感）能通過的原因。
- 槓桿/反向 ETF（如 `00631L.TW`）維持 Assumptions 的立場：**個別討論、不自動納入**。
  它們的複利路徑相依性使「日內報酬」與一般現貨不可比，混入會讓跨標的離散度
  失去意義。準則以顯式清單排除，排除理由一樣要出現在報告裡（FR-011）。

**Alternatives considered**：

- 直接沿用 `config.data.tickers`（2330/0050/00878/00919/00631L）：最省事，
  但那份清單本身沒有記錄納入理由，等於把「事後挑選」換一個地方藏起來。否決。
- 以市值或成交金額排名取前 N：客觀且事前可得，但**排名是全市場掃描**，
  需要本案沒有的資料源。列為未來可能的準則版本。

## R6：效力標籤的狀態機

**Decision**：三態，由累積長度與逐窗樣本量決定，**不可手動指定**：

| 標籤 | 條件 |
|---|---|
| `in_sample_descriptive` | 預設。累積長度不足以切出所需窗數時恆為此值 |
| `out_of_sample_insufficient` | 切得出窗，但存在任一測試窗的來回交易數 < 門檻 |
| `out_of_sample_validated` | 切得出 ≥ 3 組不重疊測試窗，且每窗每標的 ≥ 30 筆來回 |

**Rationale**：標籤若可由呼叫端指定，遲早會有人為了讓報告好看而指定它。
把它做成累積狀態的**純函式**，是唯一能讓 FR-005 在長期成立的方式。
門檻值進 `config.yaml`（憲章原則 V），但修改門檻會改變標籤版本識別，
使新舊結論不被誤當同一條件（呼應 FR-012 對準則版本的同一設計）。

**注意**：`out_of_sample_validated` 只宣稱「樣本外驗證的**程序**已執行」，
不宣稱策略有效——FR-006/SC-012 的措辭檢核對三種標籤一律適用。

## R7：參數尺度掃描的設計

**Decision**：對週期類參數施加**倍率**而非絕對值（預設倍率 `[0.25, 0.5, 1, 2, 4]`），
每個倍率輸出：四道濾網單道通過率、五道合取數、完成來回交易數。
掃描**只讀不寫**——不改 `config.yaml`，覆寫全在記憶體內（沿用 `run_b_segment.py` 的慣例）。

**Rationale**：

- 倍率而非絕對值，是因為要回答的問題是「尺度是否為瓶頸」，不是「哪個值最好」。
  後者是調參，明列範圍外。倍率曲線平坦 = 尺度不是瓶頸，這是可讀出的**反證**。
- 單道通過率是**順序無關**的量（`run_5m_evaluation.py:289` 已用此判準），
  故適合當跨尺度比較的基準；合取的逐道歸因隨排列而變，不適合。
- 掃描結果直接餵給 FR-018：`verdict()` 的處方由曲線形狀決定，
  而不是像現行 `run_5m_evaluation.py:399-406` 那樣在交易數不足時無條件輸出
  「先做參數時框化」。

**已知的現況證據**：2026-08-06 實測顯示四道濾網單道通過率皆落在 24–70%，
無一因尺度而失效。若掃描重現此結果，正確產出是**刪除該假設**（FR-018、SC-010）。

## R8：確定性如何在有隨機性的環境裡成立

**Decision**：確定性的定義域是**固定快照**，不是資料源。報告分兩區：
`inputs`（含快照指紋、參數、準則版本、標籤門檻）與 `results`（所有數值）。
SC-001 的逐欄比對只涵蓋 `results` 與 `inputs`，執行時間戳、run id、
主機資訊置於 `provenance` 區並排除在比對之外。

**Rationale**：資料源本身不可重現（實測：同一請求相隔 56 分鐘得 7 → 5 個來回），
把「可重現」定義成對資料源可重現是做不到的承諾。定義成對快照可重現，
既做得到，也正好是引用結論時真正需要的保證——指紋一致則數字必然一致。

**實作上的確定性風險點**（測試須逐一覆蓋）：

- dict 迭代順序 → 所有輸出結構於序列化前排序。
- 浮點格式化 → JSON 數值以固定小數位輸出。
- pandas groupby 的組序 → 顯式 `sort=True`。
- 標的處理順序 → 依 ticker 字串排序，不依輸入順序。

## 未決但不阻斷的項目

以下沿用 spec.md Assumptions 的預設值進入實作，因為選錯的代價是「改一個
config 值再重跑」，不是重寫設計：

- 納入準則四個維度的**具體門檻數值**（需以實際累積資料校準）。
- 排程日與時刻（預設每週一次；FR-022 只約束「顯著低於 90 天」）。
- lookback 長度（預設 20 個交易日）。
