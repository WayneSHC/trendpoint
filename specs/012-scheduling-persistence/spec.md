## 現行行為（As-Built）

本節記錄變更前的既有行為，作為驗收對照基準。**這些行為皆無 spec 覆蓋**，
係由未走 Spec Kit 的 commit 直接引入（8eb5c9f、7573e45、4df2e05）。

### 三條排程工作流

| 工作流 | 觸發時機 | 職責 | 失敗語意 |
|---|---|---|---|
| `daily_ingestion` | 每日 09:00 UTC（17:00 台北，收盤後） | 行情回填／增量入庫 | 逐標的 try/except + continue，故**另設驗證步驟**確認 TXF 連續表存在且帶 `unadj_*` 欄位，否則整條紅燈 |
| `alert_scheduler` | 週一至五 01:00–05:30 UTC 每 30 分（台股盤中） | 訊號檢測與推播；支援 `once` / `test-alert` 兩模式 | 推播管道未配置時以非零碼失敗 |
| `keepalive` | 每週一 03:17 UTC | 防止排程被停用；順帶重新啟用已被停用的工作流 | 保活提交推出後查 `pushed_at` 是否前進，未前進即紅燈 |

### keepalive 為何存在

公開 repo 若 **60 天無「儲存庫活動」**，GitHub 會自動停用所有 `schedule` 觸發的工作流
——推播與回填會安靜停止，僅寄一封通知信。關鍵限制：**只有新的 commit 算活動**，
建 tag、開 issue、合併 PR 都不重置計時器。且官方文件未載明「機器人以 `GITHUB_TOKEN`
推的 commit 是否算活動」，故該工作流不假設其有效，而是推完後查 `pushed_at` 驗證。

### 資料如何跨 run 存活（本 spec 要改的部分）

`trendpoint.db`（單一 SQLite 檔，含行情表與 `sent_alerts` 去重表）靠 **GitHub Actions
cache** 在 run 之間傳遞：寫入時 key 含 `run_id`（每次執行都產生新 entry），讀取時以
`restore-keys` 前綴比對取最近建立的一份。此機制具四個性質：

1. **LRU 淘汰**：每 repo 上限 10 GB；盤中 10 次 + 回填 1 次 = 每日 11 份快照持續累積
2. **7 天未使用即過期**
3. **branch-scoped**：feature branch 的執行讀不到 main 的快取
4. **可復活舊快照**：兩條工作流互相覆寫彼此存的檔；任一次 save 失敗或順序錯位，
   較舊的內容會蓋掉較新的——**且不會報錯**

`daily_ingestion` 已把 restore 與 save 拆開，以免回填中途失敗時丟掉已入庫進度
（否則下次要對 TAIFEX 重發 300+ 個請求）。這是對性質 4 的局部緩解，非根本解。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 累積型紀錄不再靜默回退（Priority: P1）

系統維護者需要一種儲存位置，讓「只能往前累積、不可再生」的紀錄不會因為快取淘汰、
分支隔離或工作流互相覆寫而倒退。第一個搬進去的是**推播去重紀錄**——它今天就在
承受這個問題：快取回退會讓已推播的訊號被重新推一次，快取前跳會讓該推的訊號被誤判
為已推而漏掉。

**Why this priority**: 這是本 spec 存在的理由。而且它今天就在造成實害（重複／漏推播），
不是為未來鋪路。後續 spec 013 的「帳」會是同一個儲存位置的第二個租戶，
但本 US 不依賴它——**去重紀錄自己就足以證明整套機制成立**。

**Independent Test**: 在測試中模擬「儲存內容回退到較舊版本」與「儲存內容不存在」
兩種情境，斷言去重紀錄仍完整、重複推播次數為 0。可完全獨立驗收，不需 spec 013。

**Acceptance Scenarios**:

1. **Given** 某訊號已於前一次執行推播並記錄，**When** 行情快取被淘汰後重新產生，
   **Then** 該訊號**不得**再次推播。
2. **Given** 工作流在 feature branch 上執行，**When** 讀取累積紀錄，
   **Then** 取得的是與 main 上同一份紀錄（不受分支隔離影響）。
3. **Given** 兩條工作流在時間上相鄰執行，**When** 兩者皆寫入累積紀錄，
   **Then** 後寫者不得覆蓋前寫者的內容，兩筆紀錄皆存在。

### User Story 2 - 無憑證時以本機檔跑同一份程式碼（Priority: P1）

開發者在本機、以及 CI 的測試工作流中，需要在**沒有任何外部服務憑證**的情況下
執行完整測試套件與各 `run_*.py` 入口，且跑的是與線上同一份程式碼路徑。

**Why this priority**: 與 US1 同為 P1，因為它決定了 US1 是否可測。若累積紀錄只能
在有憑證時運作，那麼 US1 的驗收就必須依賴外部服務，違反憲章 III（驗收標準必須可測試）
與既有慣例——`alerts.py` 在無憑證時退化為 Mock，正是同一個形狀。

**Independent Test**: 清空所有相關環境變數後執行 `pytest -q`，全綠且不發出任何
對外網路請求；並確認測試中的累積紀錄讀寫確實生效（非靜默 no-op）。

**Acceptance Scenarios**:

1. **Given** 未設定任何託管儲存憑證，**When** 執行測試套件，**Then** 全數通過
   且累積紀錄的讀寫行為與有憑證時語意一致。
2. **Given** 未設定憑證，**When** 執行單次訊號檢測，**Then** 去重行為正常運作
   （同一訊號不重複推播），紀錄落在本機。
3. **Given** 已設定憑證，**When** 執行任何入口，**Then** 讀寫的是託管儲存，
   且**不得**同時寫入本機檔造成兩份分歧的紀錄。

### User Story 3 - 每次執行留下可獨立還原的快照（Priority: P2）

系統維護者需要一份不依賴託管服務可用性的紀錄副本，以便在服務中斷、資料遺失、
或帳號問題時仍能還原累積紀錄，並能追溯「某一天的紀錄當時到底長什麼樣」。

**Why this priority**: 託管儲存解決了回退問題，但把唯一不可再生的資產押在單一
外部服務上是新的風險——該服務曾於 2023-12-04 發生免費層資料洩漏與遺失事故。
快照是**必要項而非選項**（見 ADR 0002）。列為 P2 是因為 US1 交付後紀錄已不會
靜默回退；快照防的是更罕見但更嚴重的整體遺失。

**Independent Test**: 取任一次執行留下的快照，在乾淨環境中還原，斷言還原結果
與該次執行後的線上內容逐筆一致。

**Acceptance Scenarios**:

1. **Given** 一次成功的排程執行，**When** 取出該次快照並在空環境還原，
   **Then** 累積紀錄與執行後的線上內容逐筆相同。
2. **Given** 託管儲存完全不可用，**When** 以最近一份快照還原至新的儲存位置，
   **Then** 系統可繼續運作，僅遺失最後一次快照之後的紀錄。
3. **Given** 累積紀錄自上次快照以來無變動，**When** 排程執行，
   **Then** 不產生內容重複的新快照（避免無意義的歷史雜訊）。

### User Story 4 - 持久化故障必須紅燈，不得安靜降級（Priority: P2）

系統維護者需要在持久化出問題時**立刻知道**，而不是幾週後才發現紀錄有洞。

**Why this priority**: 這是本專案已經付過學費的失敗模式——`daily_ingestion` 之所以
額外加一個驗證步驟，正是因為「逐標的 try/except + continue」會讓整條工作流在 TXF
完全沒進來的情況下回報 success。持久化若在有憑證的情況下改用本機檔「湊過去」，
會產生同一形狀的災難：工作流全綠，紀錄卻在分歧。

**Independent Test**: 注入「憑證存在但儲存不可達」的情境，斷言工作流以非零碼結束，
且錯誤訊息明確指出是持久化失敗（而非被誤報為推播失敗或資料問題）。

**Acceptance Scenarios**:

1. **Given** 已設定憑證但託管儲存不可達，**When** 排程執行，**Then** 該次執行
   以失敗結束，**不得**退化為本機檔並回報成功。
2. **Given** 快照步驟失敗，**When** 排程執行，**Then** 該次執行以失敗結束並明確
   指出快照未產生。
3. **Given** 憑證未設定（本機／測試情境），**When** 執行任何入口，**Then** 使用
   本機檔且**不視為錯誤**，但需在輸出中明示「目前使用本機儲存」。

---

### Edge Cases

- **憑證從有變無**：先前寫在託管儲存的紀錄，在憑證被移除後不得被本機的空紀錄
  誤判為「從未推播」而重發整批訊號 → 需要能區分「本機紀錄為空」與「查不到紀錄」。
- **同一根 bar 被判定兩次**：儲存位置改變不得影響去重鍵的語意
  （ticker, bar_time, alert_type 三元組），既有去重行為必須逐字保持。
- **行情快取遺失且累積紀錄健在**：回填必須能重建行情而不動累積紀錄；
  兩者的生命週期自此完全解耦。
- **託管儲存因閒置被封存**：免費層在閒置一段時間後會封存資料庫。排程每個交易日
  都會存取，正常不會觸發；但長假或工作流長期故障後首次執行需能自行恢復或明確報錯。
- **快照與線上不一致**：若快照產生於寫入前，還原會遺失該次紀錄 → 快照必須在
  該次所有寫入完成之後產生。
- **併發**：`daily_ingestion` 與 `alert_scheduler` 的排程時段目前不重疊，
  但手動 `workflow_dispatch` 可能造成同時執行。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 將累積型紀錄（不可再生、只能往前追加）與可再生的行情資料
  存放於**各自獨立**的儲存位置，兩者的生命週期不得互相牽連。
- **FR-002**: 累積型紀錄的儲存 MUST NOT 具備「內容可能倒退至較舊版本」的性質；
  任何已成功寫入的紀錄，在後續任何一次執行中都必須仍可讀取。
- **FR-003**: 推播去重紀錄 MUST 遷移為累積型紀錄的第一個租戶，其去重鍵語意
  （ticker, bar_time, alert_type）與既有行為**逐字不變**。
- **FR-004**: 行情資料 MUST 留在可再生的儲存（現行快取機制不變），且回填／增量
  邏輯不得因本變更而改動。
- **FR-005**: 未設定託管儲存憑證時，系統 MUST 退化為本機檔並跑**同一份程式碼路徑**，
  且在輸出中明示當前使用本機儲存。
- **FR-006**: 已設定憑證但託管儲存不可達時，系統 MUST 以失敗結束，
  **MUST NOT** 退化為本機檔。
- **FR-007**: 系統 MUST NOT 在同一次執行中同時寫入託管儲存與本機檔
  （避免產生兩份分歧的紀錄）。
- **FR-008**: 每次排程執行 MUST 在所有寫入完成後產生一份累積紀錄的快照，
  且該快照 MUST 可在無託管儲存的乾淨環境中獨立還原。
- **FR-009**: 累積紀錄自上次快照以來無變動時，系統 MUST NOT 產生內容重複的新快照。
- **FR-010**: 快照步驟失敗 MUST 使該次執行以失敗結束。
- **FR-011**: 憑證 MUST 僅經環境變數／GitHub Secrets 傳遞，MUST NOT 落入指令字串、
  日誌或錯誤訊息（比照 `alerts.py` 對 token 的處理）。
- **FR-012**: 儲存位置的連線參數 MUST 經集中組態與 schema 驗證，
  MUST NOT 硬編碼（憲章 V）。
- **FR-013**: 表名驗證與參數化 SQL 的既有防護 MUST 繼續適用於新的儲存位置
  （憲章 Security 節）。
- **FR-014**: 三條排程工作流的現行行為 MUST 以文件記錄（見本 spec「現行行為」節），
  含各自的觸發時機、職責、失敗語意，以及 keepalive 存在的原因。

### Key Entities

- **累積型紀錄（Append-Only Record）**：只能往前追加、不可再生的資料。
  本 spec 的租戶是推播去重紀錄；spec 013 的「帳」為第二個租戶。
  關鍵性質：遺失即永久遺失，無法由其他資料重算。
- **可再生資料（Regenerable Data）**：行情 K 線與衍生表。遺失可由來源重抓，
  代價是時間與對外請求量（TXF 全歷史回填約 300+ 個請求）。
- **快照（Snapshot）**：某一時點累積紀錄的完整副本，可獨立還原，
  不依賴託管服務可用性。
- **推播去重鍵（Dedup Key）**：(ticker, bar_time, alert_type) 三元組，
  用於判定某訊號是否已推播過。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 注入「儲存內容回退至較舊版本」與「儲存內容不存在」兩種情境後，
  重複推播次數為 **0**、漏推播次數為 **0**。
- **SC-002**: 在未設定任何外部服務憑證的環境中，完整測試套件通過率 **100%**
  且對外網路請求數為 **0**。
- **SC-003**: 任一次排程執行留下的快照，在乾淨環境還原後與該次執行後的紀錄
  **逐筆一致**（差異筆數為 0）。
- **SC-004**: 注入「憑證存在但儲存不可達」情境時，工作流以**非零結束碼**結束，
  且錯誤訊息明確指出持久化失敗（人工判讀確認訊息可辨識）。
- **SC-005**: 行情資料完全遺失並重新回填後，累積紀錄的筆數與內容**不變**。
- **SC-006**: 維護者能僅憑本 spec 回答三個問題——三條工作流各在何時觸發、
  資料如何跨 run 存活、keepalive 為何存在——無需閱讀任何 YAML。`[MANUAL]`

## Assumptions

- **累積紀錄的量級極小**：去重紀錄與帳皆為每日數筆，年增量以千筆計。
  據此假設任何託管方案的免費層容量都不構成限制（現行整個資料庫為 3.4 MB／52,972 列）。
- **快照的落點**：預設為「內容有變動時提交進 repo，並每次執行另存一份可下載副本」。
  提交進 repo 是為了取得永久保存與可 diff 的稽核軌跡（可下載副本通常有保留期限）；
  以「內容有變動」為條件是為了避免每日雜訊。**副作用**：這類提交會重置 60 天
  儲存庫活動計時器，使 `keepalive` 的保活職責變為冗餘——但其「重新啟用被停用的
  工作流」與健康檢查職責仍有價值，故本 spec 不移除該工作流。
- **併發不需處理**：現行排程時段不重疊，且寫入頻率為每日數筆。手動同時觸發
  屬人為操作，以「後寫者不覆蓋前寫者」（US1 情境 3）涵蓋即足夠，
  不引入鎖或交易隔離機制。
- **不搬行情資料**：行情資料遷移至同一託管儲存屬**階段二**，另立 spec
  （GitHub issue [#41](https://github.com/WayneSHC/trendpoint/issues/41)），
  觸發條件為「想把儀表板部署到本機以外」。本 spec 刻意不含該範圍。
- **外部前置條件**：託管儲存帳號需由 repo owner 自行註冊並設定 Secrets。
  此項不阻塞本 spec 的開發與測試（US2 的本機檔退化路徑），
  但阻塞 US1／US3／US4 在真實環境的驗收。
- **既有推播行為不變**：本 spec 只改「紀錄存在哪裡」，不改「何時推播什麼」。
  訊號判定、訊息格式、推播管道皆不在範圍內（後者屬 spec 013）。
