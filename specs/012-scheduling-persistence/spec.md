## 現行行為（As-Built）

本節記錄變更前的既有行為，作為驗收對照基準。**這些行為皆無 spec 覆蓋**，
係由未走 Spec Kit 的 commit 直接引入（8eb5c9f、7573e45、4df2e05）。

### 三條排程工作流

| 工作流 | 觸發時機 | 職責 | 失敗語意 |
|---|---|---|---|
| `daily_ingestion` | 每日 09:00 UTC（17:00 台北，收盤後） | 行情回填／增量入庫 | 逐標的 try/except + continue，故**另設驗證步驟**確認 TXF 連續表存在且帶 `unadj_*` 欄位，否則整條紅燈 |
| `alert_scheduler` | 週一至五 01:00–05:30 UTC 每 30 分（台股盤中） | 訊號檢測與推播；支援 `once` / `test-alert` 兩模式 | 推播管道未配置時以非零碼失敗 |
| `keepalive` | 每週一 03:17 UTC | 防止排程被停用；順帶重新啟用已被停用的工作流 | 保活提交推出後查 `pushed_at` 是否前進，未前進即紅燈 |

### keepalive 為何存在

公開 repo 若 **60 天無「儲存庫活動」**，GitHub 會自動停用所有 `schedule` 觸發的工作流
——推播與回填會安靜停止，僅寄一封通知信。關鍵限制：**只有新的 commit 算活動**，
建 tag、開 issue、合併 PR 都不重置計時器。且官方文件未載明「機器人以 `GITHUB_TOKEN`
推的 commit 是否算活動」，故該工作流不假設其有效，而是推完後查 `pushed_at` 驗證。

### 資料如何跨 run 存活（本 spec 要改的部分）

`trendpoint.db`（單一 SQLite 檔，含行情表與 `sent_alerts` 去重表）靠 **GitHub Actions
cache** 在 run 之間傳遞：寫入時 key 含 `run_id`（每次執行都產生新 entry），讀取時以
`restore-keys` 前綴比對取最近建立的一份。此機制具四個性質：

1. **LRU 淘汰**：每 repo 上限 10 GB；盤中 10 次 + 回填 1 次 = 每日 11 份快照持續累積
2. **7 天未使用即過期**
3. **branch-scoped**：feature branch 的執行讀不到 main 的快取
4. **可復活舊快照**：兩條工作流互相覆寫彼此存的檔；任一次 save 失敗或順序錯位，
   較舊的內容會蓋掉較新的——**且不會報錯**

`daily_ingestion` 已把 restore 與 save 拆開，以免回填中途失敗時丟掉已入庫進度
（否則下次要對 TAIFEX 重發 300+ 個請求）。這是對性質 4 的局部緩解，非根本解。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 累積型紀錄不再靜默回退（Priority: P1）

系統維護者需要一種儲存位置，讓「只能往前累積、不可再生」的紀錄不會因為快取淘汰、
分支隔離或工作流互相覆寫而倒退。第一個搬進去的是**推播去重紀錄**——它今天就在
承受這個問題：快取回退會讓已推播的訊號被重新推一次，快取前跳會讓該推的訊號被誤判
為已推而漏掉。

**Why this priority**: 這是本 spec 存在的理由。而且它今天就在造成實害（重複／漏推播），
不是為未來鋪路。後續 spec 013 的「帳」會是同一個儲存位置的第二個租戶，
但本 US 不依賴它——**去重紀錄自己就足以證明整套機制成立**。

**Independent Test**: 在測試中模擬「儲存內容回退到較舊版本」與「儲存內容不存在」
兩種情境，斷言去重紀錄仍完整、重複推播次數為 0。可完全獨立驗收，不需 spec 013。

**Acceptance Scenarios**:

1. **Given** 某訊號已於前一次執行推播並記錄，**When** 行情快取被淘汰後重新產生，
   **Then** 該訊號**不得**再次推播。
2. **Given** 工作流在 feature branch 上執行，**When** 讀取累積紀錄，
   **Then** 取得的是與 main 上同一份紀錄（不受分支隔離影響）。
3. **Given** 兩條工作流在時間上相鄰執行，**When** 兩者皆寫入累積紀錄，
   **Then** 後寫者不得覆蓋前寫者的內容，兩筆紀錄皆存在。

---

### User Story 2 - 本機與 CI 跑同一份程式碼路徑（Priority: P1）

開發者在本機、以及 CI 的測試工作流中，需要在**沒有任何外部服務與憑證**的情況下
執行完整測試套件與各 `run_*.py` 入口，且跑的是與線上同一份程式碼路徑。

**Why this priority**: 與 US1 同為 P1，因為它決定了 US1 是否可測。若累積紀錄的
讀寫只能在 CI 環境成立，US1 的驗收就無法自動化，違反憲章 III（驗收標準必須可測試）。
形狀比照既有慣例——`alerts.py` 在無憑證時退化為 Mock。

**Independent Test**: 在乾淨的本機環境執行 `pytest -q`，全綠且不發出任何對外
網路請求；並確認測試中的累積紀錄讀寫確實生效（非靜默 no-op）。

**Acceptance Scenarios**:

1. **Given** 本機環境（無 CI 變數、無網路憑證），**When** 執行測試套件，
   **Then** 全數通過，且累積紀錄的讀寫語意與 CI 環境一致。
2. **Given** 本機環境，**When** 執行單次訊號檢測，**Then** 去重行為正常運作
   （同一訊號不重複推播），且輸出明示「本機模式，紀錄未推送」。
3. **Given** 本機環境，**When** 執行任何入口，**Then** **不得**嘗試 commit 或 push
   ——本機的紀錄變更是工作目錄中的檔案，由開發者自行決定是否提交。

### User Story 3 - 帳未落地必須紅燈，不得靜默丟棄（Priority: P2）

系統維護者需要在帳沒有成功落地時**立刻知道**，而不是幾週後才發現紀錄有洞。

**Why this priority**: 這是本專案已經付過學費的失敗模式——`daily_ingestion` 之所以
額外加一個驗證步驟，正是因為「逐標的 try/except + continue」會讓整條工作流在 TXF
完全沒進來的情況下回報 success。帳若在 CI 中寫進了工作目錄卻沒推上去，
會產生同一形狀的災難：工作流全綠，紀錄卻沒了。

**Independent Test**: 注入「推送持續失敗」的情境，斷言以非零碼結束，
且錯誤訊息明確指出帳未落地（而非被誤報為推播失敗或資料問題）。

**Acceptance Scenarios**:

1. **Given** CI 環境且帳有新紀錄，**When** 推送在重試上限內持續失敗，
   **Then** 該次執行以失敗結束，訊息明指帳未落地。
2. **Given** CI 環境且另一次執行已推送了新內容，**When** 本次執行推送發生衝突，
   **Then** 以 rebase 重試後成功推送，**兩次執行的紀錄皆存在**、無任何一方被覆蓋。
3. **Given** 帳自上次推送以來無新紀錄，**When** 排程執行，
   **Then** 不產生任何提交（避免無意義的歷史雜訊），且**不視為錯誤**。

### Edge Cases

- **同一根 bar 被判定兩次**：儲存位置改變不得影響去重鍵的語意
  （ticker, bar_time, alert_type 三元組），既有去重行為必須逐字保持。
  **格式若被正規化，歷史訊號會全部被判為未發送而重發一輪**——一個看起來像
  「上線成功」的災難。
- **行情快取遺失且帳健在**：回填必須能重建行情而不動帳；
  兩者的生命週期自此完全解耦。
- **併發推送衝突**：`daily_ingestion` 與 `alert_scheduler` 的排程時段目前不重疊
  （01:00–05:30 vs 09:00 UTC），但手動 `workflow_dispatch` 可能造成同時執行。
  兩者同時追加帳時，後推送者必須 rebase 後重試，**不得覆蓋**先推送者的紀錄。
- **執行中途崩潰**：訊號已推播但帳尚未推送 → 下次執行會視為未發送而重發。
  此為既有 fail-open 行為的延續（憲章允許重複、禁止漏發），非本案要修的缺陷。
- **月檔邊界**：跨 UTC 月份的執行必須寫入正確的月檔；新月份的首次寫入需能
  建立新檔而非失敗。
- **淺 clone**：CI 的 checkout 若為 shallow，rebase 可能失敗 → 帳同步所需的
  git 歷史深度必須明確。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 將帳（不可再生、只能往前追加）與可再生的行情資料
  存放於**各自獨立**的儲存位置，兩者的生命週期不得互相牽連。
- **FR-002**: 帳的儲存 MUST NOT 具備「內容可能靜默倒退至較舊版本」的性質；
  任何已成功落地的紀錄，在後續任何一次執行中都必須仍可讀取。內容衝突
  MUST 表現為顯性錯誤（可重試），MUST NOT 表現為靜默覆蓋。
- **FR-003**: 推播去重紀錄 MUST 遷移為帳的第一個租戶，其去重鍵語意
  （ticker, bar_time, alert_type）與既有行為**逐字不變**，含 `bar_time`
  的字串化格式。
- **FR-004**: 行情資料 MUST 留在可再生的儲存（現行 Actions cache 機制不變），
  且回填／增量邏輯不得因本變更而改動。
- **FR-005**: 帳 MUST 為版本控制可追蹤的純文字格式，且其路徑 MUST NOT 被
  `.gitignore` 排除。`trendpoint.db` 的排除 MUST 保持不變——行情庫仍是可再生產物。
- **FR-006**: 帳 MUST 按 UTC 月份分割檔案，使單檔不隨時間無限增長，
  且衝突面收斂於當月。
- **FR-007**: 本機執行時系統 MUST 只寫入工作目錄的檔案，MUST NOT 嘗試 commit
  或 push，且在輸出中明示「本機模式，紀錄未推送」。
- **FR-008**: CI 執行時系統 MUST 在該次所有紀錄寫入完成後才進行同步
  （寫入 → rebase → commit → push），使推送內容必定包含該次的全部紀錄。
- **FR-009**: 帳自上次同步以來無新紀錄時，系統 MUST NOT 產生提交，
  且此情形 MUST NOT 視為錯誤。
- **FR-010**: 推送衝突時系統 MUST 以 rebase 後重試（重試上限為可組態值）；
  重試耗盡 MUST 使該次執行以非零碼結束，訊息明指帳未落地。
  MUST NOT 靜默丟棄該次紀錄。
- **FR-011**: 帳的內容 MUST NOT 含任何憑證或 token。CI 的推送權限
  MUST 為最小必要範圍（`contents: write`）。
- **FR-012**: 帳的路徑與重試上限 MUST 經集中組態與 schema 驗證，
  MUST NOT 硬編碼（憲章 V）。
- **FR-013**: 帳的讀寫 MUST NOT 依賴任何資料庫驅動或外部服務
  （理由見 [research.md](research.md) R1）。
- **FR-014**: 三條排程工作流的現行行為 MUST 以文件記錄（見本 spec「現行行為」節），
  含各自的觸發時機、職責、失敗語意，以及 keepalive 存在的原因。

### Key Entities

- **累積型紀錄（Append-Only Record）**：只能往前追加、不可再生的資料。
  本 spec 的租戶是推播去重紀錄；spec 013 的「帳」為第二個租戶。
  關鍵性質：遺失即永久遺失，無法由其他資料重算。
- **可再生資料（Regenerable Data）**：行情 K 線與衍生表。遺失可由來源重抓，
  代價是時間與對外請求量（TXF 全歷史回填約 300+ 個請求）。
- **推播去重鍵（Dedup Key）**：(ticker, bar_time, alert_type) 三元組，
  用於判定某訊號是否已推播過。
- **同步模式（Sync Mode）**：`ci`（寫檔後 rebase／commit／push）或
  `local`（只寫工作目錄的檔案）。啟動時判定一次，執行中不變。

**無獨立的「快照」實體。** 帳本身即耐久紀錄——它是 repo 內受版本控制的檔案，
每次同步就是一次提交，`git log -p` 即其歷史。原設計中「託管儲存 + 另存快照」
的兩層結構已收斂為一層（見 [ADR 0004](../../docs/adr/0004-ledger-as-repo-text-file.md)）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 注入「行情快取被淘汰」與「行情快取內容回退至較舊版本」兩種情境後，
  重複推播次數為 **0**、漏推播次數為 **0**。
- **SC-002**: 在無任何外部服務與憑證的本機環境中，完整測試套件通過率 **100%**
  且對外網路請求數為 **0**。
- **SC-003**: 帳的每一次變更皆可由 `git log -p <帳路徑>` 逐次追溯，
  且任一歷史版本可還原（差異筆數為 0）。
- **SC-004**: 注入「推送持續失敗」情境時，工作流以**非零結束碼**結束，
  且錯誤訊息明確指出帳未落地（人工判讀確認訊息可辨識）。
- **SC-005**: 行情資料完全遺失並重新回填後，帳的筆數與內容**不變**。
- **SC-006**: 維護者能僅憑本 spec 回答三個問題——三條工作流各在何時觸發、
  資料如何跨 run 存活、keepalive 為何存在——無需閱讀任何 YAML。`[MANUAL]`
- **SC-007**: 兩次執行併發追加帳時，兩者的紀錄**皆存在**，
  無任何一方被覆蓋（重試後的最終筆數 = 兩次執行新增筆數之和）。

## Assumptions

- **帳的量級極小**：去重紀錄目前**總共 1 列**；spec 013 的影子部位加入後為
  每日數筆、年增量以千筆計。據此假設純文字檔完全足夠，不需要資料庫
  （現行整個行情庫為 3.4 MB／52,972 列，帳與它相差三個數量級）。
- **格式與路徑**：JSONL（一列一筆），按 UTC 月分割為 `ledger/YYYY-MM.jsonl`。
  純文字是必要條件——`.gitignore` 已排除 `*.db`／`*.sqlite3`，且只有純文字
  才有 `git log -p` 的稽核價值。月分割是為避免單檔無限增長並收斂衝突面。
- **併發以重試涵蓋，不引入鎖**：現行排程時段不重疊
  （01:00–05:30 vs 09:00 UTC），衝突只來自手動 `workflow_dispatch`。
  以 rebase 重試處理即足夠（SC-007），不引入鎖或交易隔離機制。
- **`keepalive` 仍然必要**：帳的提交只在有新紀錄時發生，而目前去重紀錄
  兩週產生 1 列——提交過於稀疏，**不足以持續重置 60 天儲存庫活動計時器**。
  （spec 013 的影子部位每日落一筆後，提交才會變成每日，屆時可重新評估。）
  故本 spec 不移除 `keepalive`，其健康檢查與重新啟用職責亦仍有價值。
- **不搬行情資料**：行情資料的遷移屬**階段二**，另立 spec
  （GitHub issue [#41](https://github.com/WayneSHC/trendpoint/issues/41)），
  觸發條件為「想把儀表板部署到本機以外」。**託管方案屆時再定**——
  本 spec 不預先綁定任何供應商（見 ADR 0004）。
- **無外部前置條件**：本 spec 不需要註冊任何帳號、不需要任何 Secrets。
  US1／US2／US3 皆可在本機與 CI 完整驗收。
- **既有推播行為不變**：本 spec 只改「紀錄存在哪裡」，不改「何時推播什麼」。
  訊號判定、訊息格式、推播管道皆不在範圍內（後者屬 spec 013）。
