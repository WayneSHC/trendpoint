> 在它與「正常交易」之間沒有任何中間層：沒有「回撤達 X% 停止新進場」，

> 本案即把這些材料接成一道閘門。**注意這與 spec 012 的性質不同**：012 只是多

> 錨點更加不可或缺。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 回撤達上限時停止開新倉 (Priority: P1)

量化研究者希望系統在權益回撤達到預設上限時，自動停止開立新部位，直到回撤
回復至可接受水準才恢復。他不再需要依賴「爆倉」這個事後通知作為唯一的資金保護，
而是有一道在中途就會生效的閘門。

**Why this priority**: 本案的核心價值。現況下回撤只是報表數字，對系統行為
零影響；唯一的守門在權益歸零時才觸發。這道閘門是「爆倉」與「正常交易」之間
唯一的中間層。

**Independent Test**: 構造一段會產生連續虧損的資料，啟用閘門後，權益回撤
跨過門檻的那一刻起不再出現新進場；回撤回復後恢復進場。

**Acceptance Scenarios**:

1. **Given** 閘門啟用且回撤上限為 X%，**When** 判定根的權益回撤達到或超過 X%，
   **Then** 該根不得開立新部位（多空皆然），且原因可於交易日誌辨識。
2. **Given** 閘門因回撤而封鎖中，**When** 權益回撤回復至恢復門檻之上，
   **Then** 恢復正常進場判定。
3. **Given** 閘門封鎖中且**持有部位**，**When** 出場條件成立（停損／停利／
   時間止盈／爆倉），**Then** 出場一律照常執行——閘門絕不阻擋出場。
4. **Given** 回撤在門檻邊界反覆震盪，**When** 恢復門檻嚴格小於封鎖門檻，
   **Then** 不出現「封鎖／解除」逐根翻動（遲滯區間有效）。

### User Story 2 - 基準不被污染 (Priority: P1)

研究者需要確信：這道閘門的加入本身不改變任何既有結果。預設關閉狀態下，
所有回測、監控、組合路徑的行為與本案實作前逐筆一致。

**Why this priority**: 與 US1 同等關鍵，且比 spec 012 更關鍵——本案改變的是
**權益路徑**（少做幾筆交易 → 權益曲線不同 → 所有績效指標不同）。若基準被污染，
就無法分辨績效差異來自閘門還是附帶變更。

**Independent Test**: 閘門關閉時，同資料同參數的回測輸出（逐筆進出場、權益
曲線）與實作前逐項相等。

**Acceptance Scenarios**:

1. **Given** 預設（兩道閘門皆關閉），**When** 執行回測，**Then** 結果與本案
   實作前完全一致（逐筆比對，非僅摘要指標）。
2. **Given** 閘門關閉，**When** 執行既有全部測試，**Then** 全數維持通過。
3. **Given** 兩道閘門可獨立開關，**When** 只啟用其中一道，**Then** 另一道
   對結果零影響（可獨立歸因）。

### User Story 3 - 結算日不開新倉 (Priority: P2)

期貨交易者希望系統在台指期結算日（每月第三個週三）不開立新部位，避免在
結算日特有的價格行為與換約效應中進場。

**Why this priority**: 與 US1 共用同一道閘門出口，實作邊際成本低。但它只影響
期貨、且日期規則確定，風險與價值都小於 US1，故列 P2。

**Independent Test**: 對含結算日的期貨資料，啟用該閘門後結算日不出現新進場；
非結算日不受影響。

**Acceptance Scenarios**:

1. **Given** 結算日封鎖啟用之期貨標的，**When** 判定根為結算日，**Then**
   不開立新部位（多空皆然）。
2. **Given** 同上，**When** 判定根非結算日，**Then** 進場判定與未啟用時相同。
3. **Given** 該月第三個週三並非交易日（假日），**When** 判定結算日，
   **Then** 以資料中該日之後的第一個交易日為結算日（不得因日期不存在而靜默失效）。
4. **Given** 現貨標的，**When** 啟用結算日封鎖，**Then** 明確不適用（結算日
   是期貨概念）——行為與未啟用相同，且不得因此報錯。

### Edge Cases

- **暖機期／權益尚無峰值**：回測第一根尚無歷史峰值，回撤定義為 0，不得封鎖。
- **回撤計算的時序**：進場判定發生於迴圈當根的開頭，而當根的權益要到迴圈尾端
  才算出（`backtester.py:581`）。故閘門只能取**判定根（`i-1`）為止**的權益——
  這與訊號的 timebase 天然一致（訊號亦取 `sig_row = iloc[i-1]`），不需額外
  `.shift()`，但**必須明文寫死**，否則實作者可能誤取當根權益（看前偏誤）。
- **閘門與爆倉防護的關係**：爆倉防護（權益 ≤ 0）維持不變，本案是它之前的
  一層。兩者同時滿足時，爆倉防護的強制結清優先（它是出場，閘門不擋出場）。
- **閘門不得阻擋出場**：這是本案最危險的可能誤實作。一道會擋住停損的「風控」
  比沒有風控更糟——必須有專門測試。
- **封鎖期間的部位管理**：封鎖只影響「開新倉」。既有部位的移動停損、分批
  停利、時間止盈一律照常運作。
- **恢復門檻等於封鎖門檻**：會在邊界逐根翻動（flapping）。schema 須要求
  恢復門檻嚴格小於封鎖門檻。
- **結算日的資料層 vs 交易層**：`data_sources/rollover.py` 已處理**資料層**的
  轉倉（量最大月），但交易層完全沒有結算日概念；本案新增的是交易層判定，
  不得改動轉倉邏輯。
- **組合回測路徑**：`portfolio_backtester.py` 有自己的迴圈與權益維護。閘門
  關閉時行為不變即滿足 FR-002；是否支援啟用狀態依實作成本決定，若不支援
  須明確標註而非沉默忽略。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供一道「進場閘門」：閘門關閉（不通過）時，該根
  不得開立新部位；閘門 MUST 同時作用於多方與空方進場（無方向性）。
- **FR-002**: 閘門 MUST NOT 影響任何出場路徑（停損／停利／時間止盈／分批／
  爆倉強制結清），亦不得影響既有部位的風控狀態更新。
- **FR-003**: **回撤觸發**：當判定根為止的權益回撤（相對歷史峰值）達到或超過
  封鎖門檻時，閘門 MUST 關閉；當回撤回復至恢復門檻之上時，閘門 MUST 重新開啟。
- **FR-004**: 回撤 MUST 僅以**判定根（含）為止**已知的權益計算，不得使用
  成交根或當根尚未結算的權益（憲章原則 I）。
- **FR-005**: 恢復門檻 MUST 嚴格小於封鎖門檻（遲滯區間），並由 schema 驗證；
  相等或反向設定 MUST 被拒絕。
- **FR-006**: **結算日觸發**：對期貨標的，當判定根為台指期結算日時，閘門
  MUST 關閉。結算日定義為每月第三個週三；若該日不在資料的交易日集合中，
  MUST 取其後第一個交易日。
- **FR-007**: 結算日封鎖 MUST 僅作用於期貨資產類別；對現貨標的 MUST 明確
  不適用（行為與未啟用相同，且不得報錯）。
- **FR-008**: 兩道觸發條件（回撤、結算日）MUST 可**獨立開關**，使各自的
  期望值貢獻可分別歸因。
- **FR-009**: 兩道閘門 MUST 預設關閉。關閉時全系統（單標的回測、組合回測、
  即時監控、儀表板）行為與本案實作前**逐筆**一致。
- **FR-010**: 閘門因故關閉而未進場時，MUST 可在輸出中辨識原因（回撤封鎖 /
  結算日封鎖），使消融結果可解釋。
- **FR-011**: MUST 納入消融清單，兩道觸發條件各為可獨立停用的一項。
- **FR-012**: 新增之可調參數 MUST 集中於 `config/config.yaml` 並經 Pydantic
  schema 驗證後載入，且可經 `ticker_overrides` 逐標的覆寫（憲章原則 V）。
- **FR-013**: MUST 於 `tests/test_lookahead_bias.py` 新增防禦測試：篡改判定根
  之後的價格／權益，不得改變任何閘門判定（憲章原則 I）。
- **FR-014**: 績效比較 MUST 以扣除摩擦成本後的數字呈現（憲章原則 II）；
  **主要裁決指標為風險調整後指標（Calmar、MDD、期望值），總報酬僅供輔助**
  ——本案預期會降低總報酬（曝險下降），以總報酬裁決會導致錯誤結論。
- **FR-015**: 本案 MUST NOT 實作「縮減部位」（partial de-risking）。部位大小
  的風險化屬後續 sizing 議題（spec 014），混作一案將使兩者的績效效果無法歸因。

### Key Entities

- **進場閘門（entry gate）**: 布林判定，由回撤狀態與日曆狀態聯合決定；
  僅作用於開新倉，對出場透明。
- **權益回撤狀態（drawdown state）**: 由判定根為止的權益序列與其歷史峰值
  導出；帶遲滯（封鎖門檻 / 恢復門檻兩值）。
- **結算日集合（settlement days）**: 由資料本身的交易日集合導出的每月第三個
  週三（或其後第一個交易日）；僅對期貨有意義。
- **封鎖原因（block reason）**: 用於輸出與歸因的標記，區分回撤封鎖與結算日封鎖。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 兩道閘門皆關閉時，同資料同參數之回測結果與實作前**逐筆**一致
  （進出場時點、方向、股數/口數、損益、權益曲線逐根值），差異數為 0。
- **SC-002**: 構造連續虧損序列並啟用回撤閘門：回撤跨過封鎖門檻後不再出現
  新進場；回撤回復至恢復門檻之上後恢復進場（兩個轉折皆可指出確切根數）。
- **SC-003**: **閘門封鎖期間，所有出場路徑仍正常執行**——構造「封鎖中且持倉
  觸發停損」之情境，斷言出場確實發生（證明 FR-002）。
- **SC-004**: 篡改判定根**之後**的價格／權益（含序列尾端追加資料），不改變
  任何閘門判定與進場決策（證明 FR-004/FR-013）。
- **SC-005**: 恢復門檻 ≥ 封鎖門檻之設定被 schema 拒絕（證明 FR-005）。
- **SC-006**: 對含結算日之期貨資料啟用結算日閘門：結算日不出現新進場，
  非結算日之進場判定與未啟用時逐筆相同（證明 FR-006）。
- **SC-007**: 當月第三個週三為非交易日時，封鎖日落在其後第一個交易日
  （以構造之含假日資料驗證，證明 FR-006 後半）。
- **SC-008**: 對現貨標的啟用結算日閘門，結果與未啟用完全相同且不報錯
  （證明 FR-007）。
- **SC-009**: 兩道閘門獨立性：僅啟用其一時，另一道對結果零影響（證明 FR-008）。
- **SC-010**: 空方鏡像：以價格鏡像資料驗證閘門對空方進場的影響與多方逐項對稱。
- **SC-011**: 消融清單新增兩列（停用回撤閘門／停用結算日閘門），各列與基準列
  的交易筆數、期望值、Profit Factor、MDD、Calmar 皆有值可比較（證明 FR-011）。
- **SC-012**: 未進場之封鎖事件可在輸出中辨識其原因（證明 FR-010）。
- **SC-013**: `pytest -q` 全數通過（含既有測試無退化）。

  |---|---|---|---|
  | 2330.TW | 22 ⚠ | −45.16% | 0.4516 |
  | **0050.TW** | 16 ⚠ | −19.51% | 0.1951 |
  | 00878.TW | 7 ⚠ | −9.41% | 0.0941 |
  | 00919.TW | 6 ⚠ | −8.93% | 0.0893 |

  | **TXF** | 46 | −57.60% | 0.5760 |

  唯一達標的是 TXF（46 筆）。

  **兩個必須連帶記錄的依據問題：**

  1. **取的是帶號分布的第 5 百分位，不是第 95。** `bootstrap_trades` 回傳的
     `max_drawdown` 是帶號負值，「回撤**幅度**的 p95」對應到帶號分布的 p5。
     本專案曾在此犯錯：初版取 `[95]`，每個標的都校準出 `0.0000` 的門檻，
     於是閘門在任何設定下都不可能觸發，而報表看起來一切正常
     （見 `run_b_segment.calibrate_dd_limit` 的 docstring 與
     `tests/test_b_segment_runner.py` 的鑑別測試）。
  2. **本輪數字產出前修掉了一個會污染校準的缺陷。** 期貨的逐筆報酬率分母原本
     用 back-adjust 後的連續價（違反 spec 011 FR-004），使 TXF 的重抽深尾算出
     **−567.70%** 這種數學上不可能的權益回撤。修正後為 −57.60%。
     **凡引用本表數字者，須確認其來源 run 在 commit `15a295e` 之後**
     （PR #57；`backtester._return_basis_price` + `monte_carlo` 的輸入契約檢查）。

  **結論：本表為「參考起點」，不作為採用值。** 兩道閘門維持關閉，故 schema 中的
  `dd_limit_pct: 0.20` 仍是形式佔位、不生效。要把任一數字扶正為採用值，需先解決
  「校準門檻恆深於實際 MDD」這個結構性問題（見「B 段實測發現」第 1 點）。

## Assumptions

- **封鎖門檻預設值**：本案不預設任何「正確」的回撤上限。schema 預設值僅為
  形式上的佔位（閘門本身預設關閉，故預設值不生效），實際值須由 SC-015 以
  `monte_carlo` p95 回撤校準後決定。
- **恢復規則採遲滯（hysteresis）而非固定冷卻期數**：以「回撤回復至恢復門檻
  之上」作為解除條件，因為它與觸發條件同一量綱、只多一個參數；固定冷卻期數
  會引入「幾根」這種與市場無關的第三個旋鈕。若實測顯示遲滯不足以避免震盪，
  再議冷卻期（屬後續調整，不阻擋本案）。
- **回撤以 mark-to-market 權益計算**（含未實現損益），沿用既有權益曲線的定義
  （`backtester.py:520-537`），不另立「已實現權益」概念。
- **峰值自回測起點累計**，不設滾動窗。滾動窗峰值是另一種風控哲學，
  範圍外。
- **結算日規則以「每月第三個週三」實作**，不引入外部交易日曆套件——
  交易日集合直接取自資料本身的索引，避免新增依賴與離線 CI 的取數需求。
  台指期結算規則的歷史沿革（若曾變更）不在本案處理範圍，如有需要另立後續案。
- **本案不做縮減部位、不做風險化 sizing**（FR-015）。這是刻意的範圍切割：
  閘門改變「是否進場」、sizing 改變「進場多大」，兩者混作一案將無法歸因。
- **本案不觸碰爆倉防護**（`backtester.py:538-576`）的既有語意。
- **即時監控端**：監控目前僅推播結構訊號、不做部位與權益追蹤，故「回撤閘門」
  在監控端無等價物；本案不擴充監控端的權益追蹤能力（範圍外，且監控端與回測端
  的進場判定落差已於 spec 012 Assumptions 如實記錄，另案處理）。
- 過度配適風險：SC-014 的單一組回測對照**不足以**支撐採用決策；門檻值尤其
  容易被後見之明挑選。最終採用前應以 walk-forward 的 out-of-sample 結果確認
  （屬後續工作，不阻擋本案交付）。

## 實作期間發現（2026-07-31，A 段）

### 1. 回撤閘門在單標的路徑實為「單向閂鎖」——B 段判讀必須把這點算進去

**空手且已封鎖的帳戶無法自行恢復**：沒有部位就沒有權益變動，回撤永遠停在
封鎖時的水位，`dd >= -dd_resume_pct` 永遠不成立。因此 `dd_resume_pct` 的
解除路徑**只在「封鎖發生時仍持有部位、其後未實現損益回升」才走得到**。

這不是缺陷，是「峰值自回測起點累計 + 單一標的 + 只擋進場」三個既有決策的
必然推論。但它使回撤閘門在單標的回測中的實際語意接近「觸發後停止交易」
而非「暫停後復原」——SC-014 的數字必須在這個理解下解讀（交易筆數的下降
有相當部分來自閂鎖，而非逐次的暫停/恢復）。

連帶影響驗收設計：**兩個轉折無法在同一段「空手窗」中同時觀察**，
故 SC-002 拆成兩條路徑驗證（見 tasks.md 實作結果）。

### 2. SC-006「非結算日之進場判定與未啟用時逐筆相同」過強，已修正為前綴相等

擋掉一筆交易會改變後續的持倉狀態與可用資金，原本被「還在持倉」遮蔽的訊號
因此得以成立——閘門啟用後**必然**出現原本沒有的進場。「擋掉一筆後其餘不變」
只有在交易彼此獨立時才成立，回測不是這樣。實際驗收改為：第一次被擋**之前**
逐筆相同，且啟用後沒有任何進場落在結算日。

### 3. SC-008 的「完全相同」在欄位集層級亦成立（實作選擇）

`block_reason` 條件輸出欄的存在條件取「**實際生效**」而非「參數為真」：
對現貨標的啟用結算日閘門時不輸出該欄。contracts §3 原文為「任一閘門啟用 →
增該欄」，此處刻意收緊——一欄全為空字串只會讓使用者誤以為有風控在保護他
（與 research.md D7 對組合路徑的同一顧慮）。

## B 段實測發現（2026-08-07）

實測環境：run **31138969771**（commit `15a295e`，7 標的，`sims=5000`）。
逐項數字見 SC-014 / SC-015 條目。

### 1. 「以重抽深尾校準門檻」與「用單次回測驗證閘門有效」在方法上互斥

七個標的**無一例外**，SC-015 校準出的門檻都比該標的的實際 MDD 深，於是
SC-014 的回撤閘門封鎖 0 根。這不是資料偶然，是兩條 SC 的定義所蘊含的必然：

- SC-015 取的是**重抽分布的深尾**（幅度 p95）——「二十條可能路徑裡最壞的那條」。
- SC-014 拿**歷史上實際發生的那一條**路徑去測。

單一實現路徑的 MDD 幾乎必然淺於重抽分布的深尾（否則歷史就是二十選一的最壞情形）。
換言之：**一個被正確校準的尾部門檻，在校準它的那條序列上本來就幾乎不該觸發。**
若它經常觸發，代表門檻取得太淺，那不是風險控制而是變相的部位縮減。

因此 SC-014 在現行方法下**無法**由單次歷史回測裁決。要取得證據需改路，三個方向：

1. **樣本外**：以 A 段序列校準、在 B 段序列測（門檻不再是被測資料的函數）。
2. **合成極端路徑**：以重抽產生的深尾路徑本身作為輸入，驗證閘門在該類路徑上
   確實降低 MDD——這測的是機制而非歷史。
3. **接受閘門的定位是保險而非優化**：保險在沒出事的年份不會有正報酬，
   「零觸發」正是保費為零的表現。若採此立場，SC-014 應改寫為機制驗證
   （閘門在觸發時行為正確）而非績效比較。

**本案不自行選擇方向**——這是規格層的決定。在做出決定前，SC-014 維持「未達成」，
且**不得**以「MDD 未改善」為由宣稱閘門無效（那是把沒有證據誤讀為反面證據）。

### 2. 結算日閘門在 TXF 上讓風險變大，且成因是路徑相依而非樣本雜訊

封鎖 336 根（4.8% 的交易日）只擋掉 **1 筆**交易（46 → 45），卻使總報酬掉 12.58pp、
MDD 加深 1.37pp、Calmar 惡化一倍。交易數幾乎不變而結果差這麼多，只有一個解釋：
被擋的那一筆改寫了其後整條進場序列（擋掉一筆會改變持倉狀態與可用資金，
原本被遮蔽的訊號因此得以成立——即本規格「實作期間發現」第 2 點所述的機制）。

這使「擋掉結算日附近的進場」不能被理解為「少做一筆風險較高的交易」，
而是**整條路徑的重排**。任何以「擋掉的那幾筆表現如何」為形式的事後分析都會誤導。

### 3. MTX 的數字不具參考價值，但它暴露了校準的下界行為

MTX 仍是 mock 資料（300 根、2 筆交易）。其重抽深尾為 `0.00%`、校準門檻
`0.0000`，超出 schema 值域而回退到預設值——報告有印出提示。這條路徑值得保留：
它是「樣本少到連校準都失效」時的正確行為（回退並告知，而非靜默採用 0）。
