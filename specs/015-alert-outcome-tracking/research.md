# Phase 0 研究：推播訊號的事後表現追蹤（A 段）

**Feature**: `specs/015-alert-outcome-tracking` | **Date**: 2026-08-06

本檔記錄設計決策與**被否決的替代方案**。凡影響實作邊界者皆附 `檔案:行號`。

---

## D1：不新增 SQLite 表，JSONL 為單一真實來源

**決策**：告警紀錄的唯一儲存體是版本庫內的 JSONL 檔（月分片）。
**不新增任何 SQLite 資料表**，`sent_alerts` 維持原樣不動。

**理由**：

1. **規模允許**。一年數百列、每列約 300 bytes → 單月分片數十 KB。
   整檔讀入記憶體再處理是可忽略的成本（輪詢間隔 30 分鐘）。
2. **雙儲存體必然發散**。若同時維護 SQLite（工作用）與 JSONL（持久用），
   兩者的同步就是一個需要被測試、且會在快取逐出時進入未定義狀態的新問題。
   FR-008 要的是「紀錄不隨快取消失」——**讓它從一開始就不住在快取裡**，
   比讓它住進去再想辦法搬出來簡單得多。
3. **SC-009 由結構保證而非測試保證**。「清空重建工作資料庫後紀錄仍完整」
   在單儲存體設計下是**恆真**的，因為紀錄根本不在 `trendpoint.db` 裡。
4. **消去一整類風險**。無新表 → 無 `db_security.TABLE_NAME_PATTERN`
   （`db_security.py:19`）的相容性問題、無 schema 遷移、無新的 SQL 注入面。
   FR-022 因此只剩「回填讀取日線表」一條路徑，而它走既有的
   `safe_load_db_data`（`db_security.py:61`），已受既有防護。

**被否決的替代方案**：

| 方案 | 否決理由 |
|---|---|
| SQLite 表 + 定期匯出 JSONL | 雙儲存體同步問題（見上）。且匯出時機若在快取逐出後，該段樣本已永久遺失——**這正是本案要解決的問題本身** |
| 只用 SQLite，把 `trendpoint.db` commit 進版本庫 | `.gitignore` 明列 `*.db`；二進位檔無法 diff、無法審閱、每輪產生大 blob。且該檔含行情資料，直接觸及 A-1 的再散布疑慮（規模天差地遠） |
| 只用 GitHub Actions artifact | 有保留期限、不能累加、需下載才能讀。spec review 階段已否決 |

## D2：JSONL 路徑為 `alert_log/YYYY-MM.jsonl`，不得置於 `data/`

**決策**：版本庫根目錄新增 `alert_log/`，按月分片。

**理由**：

- `data/` **整個目錄**被 `.gitignore`，理由明列為「Yahoo Finance 資料公開再散布
  有授權疑慮」。本案紀錄含價格快照，放進去會被忽略；放進去又加例外規則，
  等於在一條有明確理由的規則上開洞。**另立目錄比開洞誠實**。
- **月分片**使單檔維持在數十 KB、diff 可讀、且天然限制單次 commit 的改動範圍。
- 憲章原則 VI 要求「可再生成的產物一律 gitignore」。本紀錄**不可再生成**——
  它是時點觀察，錯過即永久遺失，性質屬「原始輸入」。追蹤於版本庫與原則 VI
  一致，非例外（spec Assumptions A-2 已載明）。

**被否決的替代方案**：`docs/alert_log/`（它不是文件）、
`specs/015-.../data/`（規格目錄不該裝執行期產物）、
單一檔案不分片（一年後 diff 難以審閱、每次 commit 觸及整檔）。

## D3：記錄寫入為「upsert」，`notified` 是唯一可變欄位

**決策**：寫入流程為「讀入當月分片 → 依主鍵 upsert → 原子寫回」。
主鍵為 `(ticker, bar_time, alert_type)`。`notified` 允許 `false → true` 單向升級，
**永不降級**；前瞻結果欄位允許由「未回填」變為已回填，**已回填者不再改動**。
其餘欄位一經寫入即不可變。

**理由**：

純 append-only 事件日誌需要讀取端做事件摺疊（fold），對這個規模是過度設計。
但「一列一告警」又必須支援兩種後續更新：

1. **通知狀態補記**。若第一輪偵測到訊號但推播失敗，`mark_alert_as_sent`
   不會被呼叫（`monitor_signals.py:221-222`），下一輪同一根 K 線會**再次進入**
   該分支並重試推播。成功時該列的 `notified` 需由 `false` 升級為 `true`。
2. **前瞻結果回填**。見 D6。

**單向升級的必要性**：SC-005 要求「已通知成功的告警在後續輪次被去重擋下時，
其通知狀態不被改回未成功」。去重擋下時不會執行推播，若寫入邏輯無條件以
「本輪是否推播成功」覆寫該欄，已成功的列會被改回 `false`。故必須是升級而非覆寫。

**原子性**：寫入採「暫存檔 + rename」，避免行程中斷留下半截檔案。

## D4：記錄點在偵測分支內、去重判定**之前**，且不重構既有分支

**決策**：在 `monitor_signals.check_new_signals` 的七個告警分支中，
於 `alert_type` 確定後、`is_alert_already_sent` 判定**之前**插入一行記錄呼叫。
**不重構這七個分支的既有結構。**

**理由**：

- FR-001 要求記錄不得取決於通知管道是否可用。放在去重之前，
  「訊號成立」這件事就與「有沒有送出去」「之前有沒有送過」完全解耦。
- 重複偵測由 D3 的 upsert 主鍵吸收，不需要額外的守衛邏輯（FR-003）。
- **不重構是硬性約束**。既有六種告警的分支（`monitor_signals.py:217-264`）
  有大量重複，看起來很想合併——但 FR-019／SC-001 要求開關關閉時
  **逐筆逐則逐欄**與實作前相同，任何重構都會擴大 diff 並讓該保證難以驗證。
  合併重複是獨立議題，不在本案範圍。

**通知狀態的回填點**：`alert_mgr.send_alert(...)` 回傳 `True` 之後、
與既有 `mark_alert_as_sent` 同一處，補一行 `notified` 升級呼叫。

**被否決的替代方案**：

| 方案 | 否決理由 |
|---|---|
| 記錄點放在 `mark_alert_as_sent` 內 | 該函式只在推播成功時被呼叫，且其語意被明確定義為「已通知使用者」（`alerts.py:137`、`tests/test_monitor_signals.py:212`、`tests/test_alerts.py:9`）。混入研究用途會讓兩個語意糾纏，且推播失敗的訊號永遠不會被記錄——**直接違反 FR-001** |
| 先重構七個分支為資料驅動迴圈再插入 | 見上。SC-001 的驗證成本會從「讀一個 diff」變成「證明重構等價」 |
| 記錄點放在函式尾端統一處理 | 需在分支間傳遞狀態，反而更侵入既有結構 |

## D5：參數識別值用**可讀的正規字串**，不用雜湊

**決策**：參數識別值為由監控端結構參數組成的正規化字串，例如
`sp10_fvg1_fl3_sn2_vm1.5_bv0_bvm1.5_bvp20`。

**理由**：

- 參數僅 8 個，正規字串長度約 40 字元，**自我說明**且天然滿足
  「值相同 ⇒ 參數相同」（它是單射，不只是雜湊意義上的碰撞不太可能）。
- 一年後檢視樣本時，看到字串就知道那批是什麼設定跑出來的；
  看到雜湊還得回去查對照表——而那張對照表沒人會維護。
- **若採雜湊，必須用 `hashlib` 而非內建 `hash()`**：後者對 `str` 有
  per-process 隨機化（PYTHONHASHSEED），跨輪次不穩定，會讓同一組參數
  在不同執行產生不同識別值，直接違反 SC-007。此陷阱記錄於此以防日後改用雜湊。

**納入的參數**（即 `build_indicator_frame` 在監控端的結構相關輸入，
`monitor_signals.py:194-199`）：`structure_period`、`use_fvg`、`fvg_lookback`、
`swing_n`、`volume_mult`、`use_bos_volume`、`bos_volume_mult`、`bos_volume_period`。

**不納入**：`include_regime`（監控端恆為 `False`）、ATR/階梯相關參數
（不影響訊號判定，只影響記錄的參考數值）。若日後監控端開始傳入市況濾網，
此清單必須同步擴充——否則兩批不可比的樣本會共用同一個識別值。

## D6：前瞻視窗以「該標的日線序列中，日期嚴格大於告警日的第 N 根」定義

**決策**：設告警的交易日為 `D`（5 分線告警取其日期部分；日線告警即該根日期）。
T+N 為該標的日線表中**日期嚴格大於 `D` 的第 N 根**。
報酬 = `close[T+N] / 告警當下收盤價 − 1`。

**理由**：

- 此定義**同時適用兩種時框**（FR-006）：日線告警的 `D` 必然在表中，
  5 分線告警的 `D` 可能尚未入庫（當日日線收盤後才產生），
  「嚴格大於」使兩者共用一條規則，不需要為 `D` 是否存在分岔。
- 以**表中實際存在的列**計數，自動略過假日與停牌，
  不需要另行維護交易日曆（spec Assumptions A-4）。
- 基準價用**告警當下收盤價**而非 `D` 的日線收盤，是為了忠實反映
  「告警發出時使用者看到的價格」（spec Assumptions A-3）。
  代價是基準與衡量端時基不同——這使該數字**更加不可**被當作可執行策略的績效，
  已由 FR-017 的標示承擔。

**三態的區分**（FR-014／SC-014）：

| 狀態 | 條件 | 表示 |
|---|---|---|
| 已回填 | 第 N 根存在 | 數值（可為 0.0） |
| 未到期 | 日線表最後一根 ≤ `D`，或不足 N 根 | `null` |
| 資料缺漏 | 日線表不存在或讀取失敗 | `null` + 標記 |

**`null` 與 `0.0` 必須在序列化後仍可區分**——JSON 的 `null` 天然滿足，
這也是選 JSONL 而非 CSV 的附帶好處（CSV 的空字串與 `0` 需要額外約定）。

## D7：回填搭既有輪詢執行，不新增排程

**決策**：回填在每輪監控**開始時**順帶執行；另提供
`python monitor_signals.py --backfill-only` 供本機手動觸發。
**不新增 workflow、不新增 `run_*.py` 入口。**

**理由**：

- FR-012 明訂不得要求新的排程時效性。行情資料可重抓，
  日線表由既有預熱步驟維持更新（`alert_scheduler.yml:57-59`），
  回填晚幾天做完全無損正確性。
- 搭現有輪詢是**零新增基礎設施**的做法；回填本身是純計算 + 一次檔案寫回，
  對 30 分鐘一輪的節奏可忽略。
- `--backfill-only` 讓本機能在不推播的情況下補算，
  也是 SC-012（回填不發出任何對外資料請求）的驗收入口。

**被否決**：新增 `run_alert_backfill.py`（多一個入口、多一份 CLI 樣板，
而它做的事只有一個函式呼叫）、新增每日 workflow（違反 FR-012 的精神，
且多一份要維護的 YAML）。

## D8：`FR-009／SC-010` 的措辭需精確化（規格修訂）

**發現**：spec 原文 FR-009 為「當某一輪檢測未產生任何**新紀錄**時，
系統 MUST NOT 對持久化紀錄做出任何變更」，SC-010 為「執行一輪不含任何新告警的
檢測後，持久化紀錄的內容逐位元不變」。

**問題**：D7 讓回填與檢測同輪執行。一輪可能「沒有新告警」但「有前瞻結果變為可回填」，
此時檔案**應該**改變。照字面讀，回填本身會違反 FR-009。

**處理**：**修訂 spec 而非默默偏離**（憲章原則 III 禁止沉默漂移）。
FR-009 與 SC-010 補上「且無任何前瞻結果可回填」的條件。
需求的意圖不變——要防的是**無事發生的輪次產生雜訊 commit**，
而非禁止回填寫入。

## D9：commit 回版本庫的機制與其副作用

**決策**：於 `alert_scheduler.yml` 的推播步驟之後新增一個 commit 步驟，
**僅在 `alert_log/` 確有變更時**執行；commit 訊息含 `[skip ci]`。

**必要條件與副作用**（皆須在實作時處理）：

1. **workflow 需 `permissions: contents: write`**。現行 `alert_scheduler.yml`
   未宣告 `permissions`，預設值取決於 repo 設定——實作時必須顯式宣告
   （spec Assumptions A-9）。
2. **必須 `[skip ci]`**：否則每次告警的 commit 都會觸發 `tests.yml`，
   把 CI 配額耗在對純資料變更跑測試上。
3. **push 競態**：`daily_ingestion.yml` 等其他 workflow 也可能推送。
   採 `pull --rebase` 後重試；失敗時**不阻斷推播**（記錄層故障不得影響通知，FR-010），
   該輪的新列留待下一輪一併提交（upsert 冪等，重覆提交無害）。
4. **這是 CI 對預設分支的自動推送**。屬需要使用者知悉的運維行為，
   已於 spec Assumptions A-1／A-9 載明。

## D10：模組切分——新增 `alert_outcomes.py` 一個模組

**決策**：新增單一模組，內含純函式核心與薄 I/O 層。
**不切成兩個模組**（純函式 / 儲存），也不內聯進 `monitor_signals.py`。

**理由**：見 plan.md 的 Complexity Tracking。要點是核心計算
（參數識別值、交易日對齊、前瞻報酬、upsert 合併）皆為可獨立單元測試的純函式，
而 I/O 僅「讀檔／原子寫檔／讀日線表」三件事，
拆兩個模組會讓一個約 200 行的功能散成兩檔而無對應收益。

**硬約束**：此模組 **MUST NOT** 被 `ladder_system.py`、`backtester.py`、
`portfolio_backtester.py`、`walk_forward.py`、`optimizer.py`、`monte_carlo.py`
及各回測入口 import（FR-021／SC-019）。它持有告警**發生之後**的價格，
任何進入訊號鏈的讀取路徑都是未來函數的入口。此約束由靜態檢查測試守門，
不倚賴人工審查。
